# AR09 · Make 的依赖图、头文件追踪与增量构建怎样验证？

学习优先级：P1。先独立回答，再展开机制与验证。

## 直接回答

Make 依据依赖图和文件状态决定哪些目标需要重建；不是简单按源文件列表执行一遍编译。规则、自动变量和字符串函数只解决写法，工程正确性还要覆盖头文件、生成文件、编译选项和工具链变化。GCC 的 -MMD/-MP 等可在编译时生成可被 Make 引入的头文件依赖。

## 原理拆解

目标依赖前置文件，配方生成目标。$@ 指当前目标，$< 指第一个适用前置依赖，$^ 是去重后的依赖列表；$< 并不会自动循环依赖，多个源分别编译通常靠模式规则展开。GNU Make 的模式替换函数是 patsubst，不能写成不存在的 patsubset。

编译时 -MMD 记录用户头文件，-MP 生成辅助空目标以处理已删除头文件引用；再以 -include 引入对应 .d 文件。先明确默认目标，以免依赖文件改变默认入口。目录可作为 order-only prerequisite，避免目录时间戳导致所有对象重复构建。

时间戳机制不自动感知命令行编译选项或工具链变更；不同配置隔离输出目录，或显式记录配置依赖。生成头文件应声明真实依赖，不能靠“刚好先跑完”。干净构建与增量构建应在相同输入下得到一致行为。

## 例子与推演

项目有 main.c、sensor.c 和共同包含的 protocol.h。第一次生成两个 .o 及 .d；第二次不改输入应无重编译；修改 protocol.h 后两个对象都应重建；仅改 sensor.c 时只需重建 sensor.o 并重新链接。

如果头文件改后仍显示无需构建，而 clean 后才正常，这正是依赖图不完整的证据。不要把每次 clean 当长期修复，它隐藏了错误依赖并浪费时间。

## 常见误区与失败边界

变量名称 CC/CFLAGS/LDFLAGS 等应保持角色清楚；交叉编译的 CC 与 sysroot 必须面向目标。链接顺序和静态库提取规则不可当源文件通配规则处理。

.PHONY 用于不代表真实文件的入口，例如 all/check；不要把全量 clean 设成每个真实目标前置。配方通常需 Tab 或显式设置替代前缀。-n 是查看将执行的配方，不是常规构建成功证明，也不是任意递归/解析阶段副作用的安全沙箱。

## 面试追问

问：$< 为什么只编译一个文件？答：它提供一个依赖名，迭代由规则展开或你显式设计。
问：头文件改动不重编译怎么办？答：核对 .d 生成/引入和依赖链。
问：改 -D 参数后为什么旧对象还在？答：命令变化不天然成为文件依赖，需配置隔离或显式签名。

## 动手练习与验收

在自建临时工程完成“首次构建、无变化、源变更、共享头变更、删除旧头、并行构建”六种测试，保留实际执行的编译命令和目标时间戳。再用独立输出目录对比两组编译选项。

验收：每次重建集合与预测一致；生成依赖不是只在纸上出现；无变化构建不重复编译；并行执行不偶然依赖顺序。本卡未声称已编译目标固件或 Linux 内核。
