# NVIC 优先级编码与 FreeRTOS ISR 边界审计

学习优先级：P1。本文是可选深度实验，不新增核心题号。先读 [AR04](../30-architecture/ar04.md)、[RT06](rt06.md)、[RT07](rt07.md) 与 [MC05](../40-mcu/mc05.md)。目标是把“中断优先级别配错了”变成能逐项复核的整数、配置与调用上下文合同。

## 直接回答

### 30 秒回答

Cortex-M 的中断优先级数值越小，紧急程度越高；任务优先级是另一套概念。CMSIS `NVIC_SetPriority` 接收未左移的逻辑优先级，硬件优先级字节只实现高位。PRIGROUP 决定这些位怎样分成抢占优先级和子优先级。本章指定的 FreeRTOS ARM_CM4F 端口要求调用 ISR API 的外部中断处于可被内核 BASEPRI 临界区屏蔽的范围，且配置不能留下子优先级位。写了 `FromISR` 后缀，不能自动使一个过高紧急度的 ISR 合法。

### 2 分钟回答

先记录目标的 `__NVIC_PRIO_BITS`，再分清三种值：CMSIS 的逻辑优先级、IPR 中的左移后字节、AIRCR 的 PRIGROUP 原始字段。以固定 STM32F407 头文件的 4 位为例，逻辑 5 编码成 `0x50`。若把已左移的 `0x50` 又传给 `NVIC_SetPriority`，它再次左移并取字节，结果是 0，恰好成为最紧急的可配置优先级。

若内核门槛是寄存器形式 `0x50`，逻辑 2 的中断不能调用内核 API；逻辑 5、10 通过本章的优先级门槛。但还要逐项检查该 API 是否允许 ISR 调用、对象寿命、参数、失败处理和是否需要请求任务切换。高紧急度中断可以做有界、独立的采集，再用经过设计的低紧急度中断或任务交接；不能把屏蔽中断、`volatile` 或一次单字写误当成完整的拥有权协议。

### 深入回答的检查顺序

1. 芯片头文件、内核版本和实际移植端口是什么？
2. `NVIC_SetPriority` 输入是逻辑值，还是寄存器值？
3. 实际 AIRCR.PRIGROUP 与优先级位分配是什么？厂商分组宏展开后是什么数？
4. 每个调用内核 ISR API 的中断，编码后的值是否落在门槛内？
5. 是否有库在调度启动前后重新设置了分组或外设优先级？
6. 中断的处理、交接和队列满策略是否有界？能否记录中断入口、唤醒和任务执行三种不同时间点？

## 三种数字不能混用

设实现位数为 B，逻辑优先级为 L，且 `0 <= L < 2^B`。硬件字节形式是 `R = L << (8-B)`；未实现的低位不属于有效配置。这里 B=4，所以逻辑 0～15 对应 `0x00`、`0x10`……`0xf0`。这只是固定示例，不代表所有 STM32 或 Cortex-M 都实现 4 位。

| 你看到的值 | 含义 | B=4 的例子 |
| --- | --- | --- |
| `NVIC_SetPriority(irq, 5)` 中的 5 | CMSIS 逻辑值 | 正常编码到 `0x50` |
| `configMAX_SYSCALL_INTERRUPT_PRIORITY` | 本端口用的寄存器字节形式 | 门槛 `0x50` |
| 某项目自定义 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY` | 常用应用辅助宏，不是 CMSIS 参数自动转换器 | 可定义为逻辑 5，再显式左移 |
| AIRCR.PRIGROUP | 分组原始字段，0～7 | 本示例可选原始 3 |
| `NVIC_PRIORITYGROUP_4` | STM32F4 HAL 宏名 | 本固定头文件展开为原始 `0x3` |

CMSIS 的设置函数做左移和字节屏蔽，不是本章的严格输入检查器。错误输入 `NVIC_SetPriority(irq, 0x50)` 在 B=4 的整数表达式中变成 `0x00`。实际硬件是否已使能该 IRQ、何时发生 IRQ，是另一层问题；主机演示只展示编码错误。[CMSIS 设置与编码实现](https://github.com/ARM-software/CMSIS_6/blob/v6.1.0/CMSIS/Core/Include/core_cm4.h)、[HAL 分组定义](https://github.com/STMicroelectronics/stm32f4xx-hal-driver/blob/1f6451c3e07728b4c830744de380e56bf5bc0026/Inc/stm32f4xx_hal_cortex.h)

## 抢占优先级与子优先级

本章 1～7 位模型使用 CMSIS 的分组算术：抢占位数 `min(B, 7-PRIGROUP)`，子优先级位数为剩余位数。抢占字段较小，才在优先级关系上允许抢占；同一个抢占字段内，较小的子优先级用于决定符合条件的待处理中断次序，不会因此抢占正在执行的同组中断。优先级关系并不是完整的中断进入条件，还受使能、挂起、屏蔽和当前异常状态影响。

| B=4 时的原始 PRIGROUP | 抢占位 / 子优先级位 | 本章 FreeRTOS 门槛模型接受吗？ |
| --- | --- | --- |
| 0、1、2、3 | 4 / 0 | 接受 |
| 4 | 3 / 1 | 拒绝 |
| 5 | 2 / 2 | 拒绝 |
| 6 | 1 / 3 | 拒绝 |
| 7 | 0 / 4 | 拒绝 |

因此，`NVIC_PRIORITYGROUP_4` 的“4”表示 HAL 约定的 4 个抢占位，不是把 AIRCR.PRIGROUP 直接写成 4。也不能只记“必须分组 0”：在本章 B=4 的端口断言里，原始 0～3 都没有实现的子优先级位；应核对实际字段和库约定。固定端口对 8 个已实现位另有特别检查，本模型明确不覆盖，不能从模型拒绝 8 推出硬件或该端口不支持 8。[端口启动时的位数与分组检查](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/dbf70559b27d39c1fdb68dfb9a32140b6a6777a0/portable/GCC/ARM_CM4F/port.c#L345-L425)

## BASEPRI 门槛与 FromISR 合同

在本章有效分组下，BASEPRI 设置为非零门槛 T 时，数值不小于 T 的可配置中断落在其屏蔽范围。数值更小的中断更紧急，不在这个门槛的保护范围；BASEPRI=0 不提供这类屏蔽。因此本端口要求系统调用门槛非零，并检查未实现低位没有被错误置位。

设逻辑门槛为 5，寄存器门槛为 `0x50`：

| 外部 IRQ 设计用途 | 逻辑值 | 寄存器字节 | 内核此 BASEPRI 临界区会屏蔽？ | 通过 ISR API 优先级门槛？ |
| --- | --- | --- | --- | --- |
| 高紧急度采样 | 2 | `0x20` | 否 | 否 |
| UART 数据交接 | 5 | `0x50` | 是 | 是 |
| 后台完成事件 | 10 | `0xa0` | 是 | 是 |

最后一列不是“整段 ISR 已经正确”的认证。`vPortValidateInterruptPriority` 检查当前外部中断的优先级字节与门槛，并检查分组；项目还应启用合适的 `configASSERT`，在调试配置中尽早发现错误。默认优先级 0 也不能因为“我没改过它”就调用内核 API。[ISR 优先级校验](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/dbf70559b27d39c1fdb68dfb9a32140b6a6777a0/portable/GCC/ARM_CM4F/port.c#L853-L907)

还需要逐项回答：

- 用的是该版本实际存在、明确允许 ISR 的接口吗？互斥量合同不能靠换一个函数名移植到 ISR。
- 接口需要零阻塞参数、独立的唤醒标志或特定的退出切换宏吗？遵守该端口与 API 的接口合同，不凭空统一所有接口。
- 队列或通知对应对象是否已初始化，删除后有没有迟到的 IRQ？指针对象谁拥有？
- 队列满、计数合并、突发积压会怎样？ISR 不能因失败进入无界重试。
- 外设清中断、读写状态寄存器和 DMA 完成确认的次序，是否按该芯片参考手册？本文没有替所有外设决定次序。

NMI 和 HardFault 不属于这张外部可配置 IRQ 表；函数名包含 ISR 也不保证能在这些异常里调用。M0/M0+ 与 ARM_CM4F 的屏蔽实现不相同，应换读实际移植端口，不把 BASEPRI 方案直接搬过去。

## 场景：高紧急度采样与任务处理怎样交接

需求不是“采样 IRQ 必须调用队列”，而是“在证实的时间预算内获取样本，并在任务中处理”。一种候选结构是：

1. 逻辑 2 的高紧急度 IRQ 只做明确有界的采集与必要外设确认，不调用 FreeRTOS API。
2. 通过专门设计的、容量有限的存储协议移交采样记录；证明不会覆盖仍由读者使用的记录。普通全局指针和 `volatile` 标志不足以提供完整合同。
3. 让另一个处于允许门槛的外部 IRQ 或任务完成内核通知。怎样触发这个低紧急度路径，是板级设计的一部分。
4. 消费任务区分“收到交接通知”和“外设/DMA 已停止使用缓冲”。清理、超时或关闭设备时，还需要让所有在途用户停止。
5. 采样、通知和任务处理分别留时间戳或序号，测量端到端预算和丢样；模型不提供硬件延迟数值。

该方案是否适用，取决于项目对丢失、覆盖、缓存、并发和停机的要求。也可能通过修改 IRQ 紧急程度，让采样 ISR 本身处于合法门槛。两种取舍都应给出测量和寿命证据，不把“中断更高”当成永远更好的设计。对象交接继续读 [C++ 发布与复用合同](../10-c-cpp/publication-ownership-contracts.md)，DMA 资源生命期继续读 [DMA 取消与移除合同](../80-linux-drivers/dma-lifecycle-contracts.md)。

## 原创主机实验

资源： [模型源码](../../examples/python/nvic_priority_contract.py)、[有界测试](../../tests/test_nvic_priority_contract.py)。Python 3.10+；只使用标准库。

```sh
python3 examples/python/nvic_priority_contract.py
python3 -m unittest discover -s tests -p test_nvic_priority_contract.py -v
```

核心数学关系如下；完整文件还包含严格的范围检查与配置对象：

```python
def implemented_partition(bits, group):
    preemption = min(bits, 7 - group)
    return preemption, bits - preemption


def raw_priority(bits, logical):
    return logical << (8 - bits)
```

这里的短片段只解释算术，调用者必须使用完整模型的输入检查；它不是向 NVIC 寄存器写入的驱动代码。完整模型故意拒绝超范围字段，而 CMSIS 编码函数会屏蔽字段。拒绝策略是教学审计的选择，不能把两者在无效输入上的行为说成相同。

11 个测试方法检查：1～7 位、全部 8 种分组的编码解码；全部有效寄存器编码；4 位下全部候选/当前优先级关系；支持范围内全部有效门槛与 IRQ 关系；同抢占字段不同子优先级；HAL 宏原始值；重复左移；零门槛、低位错误、越界、布尔值和超范围字段的拒绝。实际运行全部通过。有限域整数测试验证的是这个原创模型的规则；它不证明目标中断已正确配置，也不证明真实 API、调度器或交接协议无竞态。

## 追问链与分级验收

| 追问 | 合格答案应能具体给出什么 |
| --- | --- |
| “优先级越大越高”对吗？ | 先区分任务与 NVIC，给出逻辑 2 与 5 的实际编码 |
| 为什么 `0x50` 传 CMSIS 会出错？ | 展开一次移位与字节屏蔽，而不是只说“要注意” |
| 同抢占级别、子优先级不同会嵌套吗？ | 不能靠子优先级抢占；区分待处理排序与抢占关系 |
| HAL 的 GROUP_4 是 raw 4 吗？ | 查固定宏值，本示例 raw 3；不推广到未核对的 HAL |
| 门槛 5 的 IRQ 5 能调用 API 吗？ | 优先级门槛包含等号；其余 API、寿命和失败合同仍要检查 |
| 比门槛更紧急的 IRQ 怎样发通知？ | 有界采集、独立交接、合法上下文通知与积压策略 |
| 为什么有时开机正常、加一个库就挂？ | 复核库是否重设分组/优先级、调度启动时点与断言记录 |
| 中断很快，任务为什么仍然晚？ | 分开入口、交接、唤醒与实际运行；测量阻塞、调度和积压 |

基础验收：解释三个数字，算对 4 位编码，知道门槛方向。进阶验收：复核真实头文件、分组、所有内核 API 调用点及对象关闭路径。项目验收：给出目标读回值、断言、逻辑分析/追踪的测量口径、突发与停机故障注入记录。本章仅完成主机层，不宣称最后一层已经完成。

## 常见坑

- 把“高优先级”省略成一个数字，不说明任务还是 NVIC、逻辑还是寄存器。
- 把已左移值传给 CMSIS，或把逻辑门槛不左移就交给本移植端口。
- 所有 MCU 一律写 4 位，忽略目标头文件与移植端口差异。
- 把 HAL 宏名称当成 AIRCR 原始字段。
- 把子优先级解释成同组抢占，或在本指定内核配置中留下子优先级位。
- 因为名字是 `FromISR` 就忽略 IRQ 紧急程度、NMI/HardFault 和 API 细项。
- 中断优先级门槛通过后，忘记对象删除、缓冲复用、队列满和设备仍在访问内存。
- 只跑主机整数测试，却在简历或文档中称“已验证中断实时性”。
