# 可选诊断补充 · 用崩溃快照建立可复核的证据链

学习优先级：P2。先掌握 [DB02 的调试基础](db02.md)、[LX08 的观测方法](../70-linux-apps/lx08.md)和 [C07 的对象寿命](../10-c-cpp/c07.md)。本章补充 Linux 用户态事后分析，不增加核心题号，也不替代板级 HardFault 或内核 crash 分析。

## 直接回答

core 文件保存某次进程状态，不是此前每一步执行的录像。先确认快照属于哪个进程、哪次部署、哪种架构和哪份二进制，再用匹配符号解释线程、寄存器、调用栈与内存。崩溃指令告诉你错误在哪里显现，未必告诉你错误最早在哪里发生。

本章的命令合同按 2026-10-10 核读的 GNU GDB 在线手册；其首页标明开发快照 19.0.50.20261009-git，不是本章宣称已安装或执行的版本。目标环境需另记实际 GDB、内核、libc、编译器和收集器版本。

## 原理拆解

### 1. 先分清“崩溃”“已收集”“可解释”

退出、收到信号、生成 core、成功保留 core 和得到可信回溯是五个不同事实。没有当前目录下的文件，不能直接推断没有崩溃或没有收集。Linux 的输出路径可能交给管道收集器；文件权限、空间、资源限额和进程可转储属性也会影响结果。某些内存映射可能不包含在快照中。先读取授权范围内的进程/服务记录和收集配置，别为“让测试通过”关闭保护或修改全局转储策略。[core(5)](https://man7.org/linux/man-pages/man5/core.5.html)说明这些条件；[内核 core_pattern 文档](https://docs.kernel.org/admin-guide/sysctl/kernel.html#core-pattern)说明输出路由。

对一次合成测试可以预先规定：收集对象仅为自己启动的测试进程，数据全为生成的占位内容，磁盘上限和保留时间有限。生产 core 可能包含口令、会话、个人数据、业务载荷和密钥；应在受限位置保存原件，按授权提取最少量摘要，不上传到公开仓库、聊天示例或未经批准的诊断服务。

### 2. 三类身份不要混成一个文件名

- 部署身份：实际运行的发布物、构建记录、目标架构、依赖库和配置。需在部署或采集时记录；崩溃后重新编译“同一份源码”不能证明二进制相同。
- 工件身份：对收集后的 executable、core、独立 debug 文件和目标库分别计算摘要，保证后续使用的是这组原件。摘要只能识别字节，不能独自证明哪份 executable 生成了 core。
- 解释身份：GNU build ID/debug link 等关联符号的方法，以及 GDB 的架构、库搜索路径和源路径设置。装上能打开的符号文件，不等于匹配成功。

将 release 标签、编译选项、链接布局、build ID、文件摘要、收集时间、已知缺失项和访问范围记录在一份受限清单。发布物已 strip 时，保留同次构建的符号包；不同优化参数、链接次序或依赖版本都可能改变地址/布局。[GDB 独立调试信息文档](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Separate-Debug-Files.html)说明 debug link、build ID 和查找方式。

### 3. 离线打开，不自动扩大信任

下面是待在目标工具环境验证的示意命令，不是已执行记录。路径都是示例占位，先替换为受限目录中的匹配文件。`-nx` 跳过初始化文件，提前关闭自动加载和 debuginfod 查询，避免解释外部工件时顺便执行附带脚本或向外查询缺失符号。

```text
gdb -nx -q -iex "set auto-load off" \
    -iex "set debuginfod enabled off" \
    ./archived-app.elf ./captured.core
(gdb) info files
(gdb) info sharedlibrary
(gdb) info threads
(gdb) thread apply all backtrace
(gdb) frame 0
(gdb) info registers
```

`file`/`core-file` 也可分别加载 executable 和 core；core 并不保证包含整个地址空间。跨目标分析需使用支持目标架构的 GDB，并提供对应的目标库，不用宿主机“名字一样”的 libc 来填空。`set sysroot` 的路径应指向匹配的目标根文件系统归档。[GDB Files](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Files.html)

全局关闭 auto-load 也可能使线程辅助库或格式化支持不可用；若缺少线程信息，先记录限制，再在已验证来源与权限的边界内配置必需的本地辅助支持，不能把关闭功能后缺失的回溯当“只有一个线程”。不把 `auto-load safe-path` 放宽到任意目录。[自动加载合同](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Auto_002dloading.html)与 [debuginfod 设置](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Debuginfod-Settings.html)给出准确选项。

### 4. 从当前线程扩展到整个故障场景

先保留信号、程序计数器和当前线程回溯，再查看其他线程是否持锁、等待队列或执行关闭流程。`backtrace` 默认只针对当前线程，`thread apply all backtrace` 才请求逐线程信息。选中某个 frame 后，再读取该帧对应的参数、局部变量和必要地址；不要根据相邻一次运行的地址解释这次快照。[GDB Backtrace](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Backtrace.html)、[Threads](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Threads.html)

每条结论写成“观察→假设→缺失证据→下一次区分性实验”。优化后变量可能显示为 optimized out；栈破坏、缺少展开信息或错配库也会使调用链不完整。缺失变量不是它等于零，也不是它从未存在。不要为了得到漂亮栈而换成不同二进制后继续称这是原事故证据。

### 5. 观察点只能加入后续复现

core 中一块内存已经变坏，不能对它设置 watch 后倒推出之前的写入者。后续在受控、授权的复现里，才可观察关键字段的修改，并记录命中线程/指令/对象寿命。硬件资源、宽度、访问范围以及软件观察点的线程/时序局限都需要检查；停机和单步会改变运行行为。[GDB Watchpoints](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Set-Watchpoints.html)

若怀疑越界或释放后使用，结合 [C07](../10-c-cpp/c07.md) 的全部别名与所有者合同，再选适用的 sanitizer 或最小复现。一次工具报警或观察点命中只是新增证据，不能替代对正常负载、优化、并发和失败路径的复验。

## 原创推演 · 上传线程在释放路径崩溃

假设某合成服务有采集、编码、上传三个线程。收集记录说上传线程收到错误信号；快照中最后一帧位于释放路径，两个其他线程分别在等待队列和编码。以下都是教学假设，不是实际事故或已执行结果。

| 已见证据 | 仍可能的解释 | 下一项能区分的检查 |
|---|---|---|
| 释放时失败 | 更早的越界、重复释放、错误指针或堆元数据破坏 | 核对对象创建/交接/销毁记录，缩小到同类合成输入 |
| 上传队列中有相同地址 | 合法引用或两个消费者误以为独占 | 核对每条队列项的所有权协议与取消路径 |
| 另一个线程仍在编码 | 正常并行或对象已释放但仍被引用 | 检查同一个实例的寿命，不只比较裸地址；地址可能复用 |
| 最后一次修改者未知 | 快照没有历史 | 在复现中加入受控实例编号、有限日志或适用观察点 |

第一份结论应是“释放路径发现损坏，原因仍待区分”，不是“free 有 bug”或“上传线程造成全部损坏”。修复后再注入队列取消、生产者退出、重复关闭和分配失败；验收应覆盖所有权状态转换，不能只证明一次正常上传结束。

## 动手练习与验收

1. 用自己的合成小程序建立 executable、独立 debug 文件和工件摘要清单；验证同次构建的 stripped 文件/debug 文件关联。不同文件名相同不算匹配。
2. 在允许采集的测试环境另做 core 收集和离线加载；记录目标、工具版本、数据范围、收集限制及是否成功。没有授权或工具时明确标未执行。
3. 故意给清单换一份不同构建的 executable；验收流程应拒绝继续声称符号已匹配。再测试缺失符号、缺失库、部分内存、优化变量和不完整展开。
4. 给上表各写一个有边界的后续实验和停止条件；保留不能证实的项，而不是补写不存在的栈或输出。

本章准备阶段实际在 Linux 主机执行了 10 项原创测试，覆盖受控 ELF/独立符号工件与清单模型；使用 Python 3.12.14、GCC 14.2.0 和 GNU objcopy/readelf 2.44。没有安装或运行 GDB，没有生成或加载真实 core，没有实际信号崩溃、观察点、内核 crash、设备或板级实验。这些缺口不会因工件测试通过而关闭。
