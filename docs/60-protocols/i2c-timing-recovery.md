# I²C 时序预算、上拉区间与有界总线恢复

学习优先级：P2，可选补充。先读 [PR01 起止、应答与总线共享](pr01.md)；Linux 接口问题回到 [LX12 子系统接口](../70-linux-apps/lx12.md)。本页不重讲地址表示、I2C_RDWR 或完整驱动，只把一次组合读的边沿、被动上拉的可行区间和恢复退出条件连起来。

正文、数值实例和主机模型为原创。规范核对固定为 NXP UM10204 Rev.7.0，2021-10-01；讨论普通开漏 Standard-mode/Fast-mode，不外推 Hs-mode、UFm、I3C、SMBus 超时或任意电平转换器。没有访问真实硬件，没有做电气、示波器、板卡或 MCU 外设测试。

## 直接回答

确认组合读不能只看字节日志：第九钟由谁接管 SDA、最后一字节的 NACK 和 STOP 必须落到实际边沿。确认上拉不能只说“用 4.7 kΩ”：小电阻受低电平吸电流约束，大电阻受 RC 上升时间约束，还要扣除容差。确认 bus-clear 不能只说“打九个时钟”：SCL 必须真的变高，每次等待和整次恢复都要有界，未释放、STOP 失败和空闲检查失败必须退出。

## 原理拆解

### 一 先把指令、引脚电平与有效采样分开

开漏“输出 1”通常意味着释放，不意味着线路立即到达高阈值。SDA/SCL 的实际高低由所有低驱动、上拉和线路共同决定。时钟拉伸时，控制器释放 SCL 仍可能读到低；高周期应从实际达到相应高阈值开始核对，而不是从软件写寄存器开始计时。[UM10204 Rev.7.0，§3.1.1–3.1.3、§3.1.9](https://www.nxp.com/docs/en/user-guide/UM10204.pdf#page=8)

下面只抽取本页用到的时序约束；不是完整符合性表。数值按规范印刷页 44 的 Table 11，测量定义见印刷页 45 的 Figure 38。§6.1 与 §7.1 中存在指向 Table 10 的文字，但总线时序行在本版本实际标为 Table 11；Table 10 是 I/O 级特性，不应因此混用。

| 约束 | Standard-mode | Fast-mode | 本页核对点 |
|---|---:|---:|---|
| fSCL 上限 | 100 kHz | 400 kHz | 达到单个高/低周期下限不自动保证总周期 |
| tLOW 下限 | 4.7 μs | 1.3 μs | 按实际阈值定义测量 |
| tHIGH 下限 | 4.0 μs | 0.6 μs | 释放到达高阈值的时间另算 |
| tSU;DAT 下限 | 250 ns | 100 ns | 第九钟的 ACK 也需要准备时间 |
| tr 上限 | 1000 ns | 300 ns | 指 30%→70% 的上升时间 |
| tr 下限 | 未列数值 | 20 ns | 太快也不是无条件合规 |
| tSU;STO 下限 | 4.0 μs | 0.6 μs | SCL 高后再结束 STOP 的准备时间 |
| tBUF 下限 | 4.7 μs | 1.3 μs | STOP 后到下一 START 的空闲间隔 |

[UM10204 Rev.7.0，§6.1、Table 11、Figure 38](https://www.nxp.com/docs/en/user-guide/UM10204.pdf#page=44)。START/repeated START 的建立与保持、下降时间、tVD;DAT/tVD;ACK、输入滤波等仍需读整张表和脚注。Table 11 注 [2] 特别要求 SCL 下降到 0.3VDD 以下后，再让 SDA 穿过不确定区；“软件先写 SCL、马上写 SDA”不能证明板上满足。

原创预算例：Fast-mode 取 tLOW=1.3 μs、tr=0.3 μs、tHIGH=0.6 μs、tf=0.3 μs，则一个按这些阈值拆开的周期是 2.5 μs，即 400 kHz。若只用 1.3+0.6 得到 526.3 kHz，既漏算转换过程，也超过模式上限。这是算术例，不是 MCU 分频寄存器配方；引脚延迟、量化、拉伸和控制器的内部计时定义还要加入。

### 二 ACK 和 NACK 是 SDA 所有权的交接

普通数据字节的八位由当前 transmitter 发送，紧随的第九位由 receiver 表达应答；第九个 SCL 仍由 controller 产生。transmitter 释放 SDA，receiver 在第九钟高期间保持相应电平。读数据时 controller 是 receiver，因此最后 NACK 是 controller 主动结束读的信号。[UM10204 Rev.7.0，§3.1.5–3.1.6、§3.1.10，Figure 12–13](https://www.nxp.com/docs/en/user-guide/UM10204.pdf#page=10)

本页数字模型用 `L` 表示拉低，用 `Z` 表示释放。`Z` 不是强推高；双方 `Z` 时才由本模型的理想上拉得到 1。驱动交接放在 SCL 低期间，下一次实际上升沿前已经准备好。若 ACK 方等到第九钟已经高了才拉低，就会制造 SCL 高期间的 SDA 下降，可能被当作 START；它不能算“晚一点的正常 ACK”。

## 例子与推演

### 三 组合读的每个边沿都能解释

原创课堂设备：普通 7 位地址 0x50，寄存器 0x12，按其假设的寄存器协议返回 0xA5、0x3C。寄存器宽度、是否自增和是否必须 repeated START 属于该设备的协议假设，不由 I²C 通用规范替所有设备规定。

事务骨架：S → 0xA0 → target ACK → 0x12 → target ACK → Sr → 0xA1 → target ACK → 0xA5 → controller ACK → 0x3C → controller NACK → P。

对于前三个 controller 发送字节，逐位通用步骤是：

1. SCL 实际低：controller 按 bit7→bit0 选择 SDA=L/Z，target 释放。
2. SDA 建立后，controller 释放 SCL；等待实际高，receiver 在有效高段读取该位。
3. controller 拉低 SCL；保持当前 SDA 到满足下降/保持要求，再准备下一位。
4. bit0 的第八钟下降后，controller 释放 SDA；target 在低阶段接管并拉低，准备 ACK。
5. controller 释放 SCL形成第九钟；此时 controller=Z、target=L、SDA=0。
6. 第九钟下降并满足保持要求后，target 才释放 SDA。这个下降沿不可因为“字节已 ACK”而省掉。

0xA0 的高段采样依次是 1 0 1 0 0 0 0 0；0x12 是 0 0 0 1 0 0 1 0；0xA1 是 1 0 1 0 0 0 0 1。每个字节后都有独立的第九钟，不能把地址 R/W 的第八位当成 ACK。

repeated START 的衔接：寄存器 ACK 的第九钟下降→双方释放 SDA、此时 SCL 低→释放 SCL并确认高→controller 拉低 SDA形成 Sr→保持规定时间后拉低 SCL→准备 0xA1。中间没有 STOP，也不把 Sr 前的 SCL 上升沿计成一个完整数据位；模型把它单独标为 `SR_SCL_RISE`。[UM10204 Rev.7.0，§3.1.4、§3.1.10、Figure 13](https://www.nxp.com/docs/en/user-guide/UM10204.pdf#page=14)

读回 0xA5 的八个有效高段是 1 0 1 0 0 1 0 1，此时 target 发数据，controller 始终释放 SDA。第八钟下降后 target 释放 SDA，controller 在低段拉低作 ACK；第九钟高段 SDA=0；第九钟下降后 controller 释放，让 target 准备下一个字节。

最后 0x3C 的八个高段是 0 0 1 1 1 1 0 0。最后一个 0 必须与结束 NACK 分开：

| 阶段 | SCL | controller SDA | target SDA | SDA 与意义 |
|---|---:|---|---|---|
| 最后 bit0 的第八钟高段 | 1 | Z | L | 0，仍是数据 |
| 第八钟下降后、NACK 准备 | 0 | Z | Z | 释放到 1，按实际上升/建立预算等待 |
| 第九钟上升及有效高段 | 1 | Z | Z | 1，controller 以释放表达 NACK |
| 第九钟下降后 | 0 | Z | Z | 完整结束应答位 |
| STOP 准备 | 0 | L | Z | SDA=0；只在低 SCL 下拉，不制造 START |
| STOP 的 SCL 变高、保持准备时间 | 1 | L | Z | SDA 仍为 0 |
| controller 释放 SDA | 1 | Z | Z | SDA 0→1，形成 STOP |
| 后续空闲观察 | 1 | Z | Z | 满足 tBUF 后才准许新 START |

这五个字节总共是 5×9=45 个数据/应答采样钟。Sr 和 STOP 准备各有另行标记的 SCL 上升；不能把采样钟计数与所有引脚上升沿总数混称。模型中最后 NACK 双方都释放，没有“驱动 SDA 高”的操作。

### 四 被动上拉要得到一个区间

以下集中 RC 模型只适用于相应开漏被动上拉、统一阈值假设。SDA 与 SCL 要分别计算：器件数量、线路、连接器、测量探头和驱动能力可能不同。[UM10204 Rev.7.0，§7.1，Equation 1–2、Figure 41–42](https://www.nxp.com/docs/en/user-guide/UM10204.pdf#page=50)

原创推导：理想放电到 0 后，V(t)=VDD×(1−exp(−t/RC))。到 30% 需约 0.356675RC，到 70% 需约 1.203973RC，因此两阈值间 tr≈0.8473RC。故：

- 低电平吸电流给出 R_sink_min=(VDD_max−VOL_max)/IOL_guaranteed。
- 最大上升时间给出 R_rise_max=tr_max/(0.8473×Cb_max)。
- 若模式有 tr_min，理想 RC 的最小上升时间再给出 R_rise_min=tr_min/(0.8473×Cb_min)。
- 实际电阻下界为 max(R_sink_min, R_rise_min)，上界为 R_rise_max。

IOL_guaranteed 是所有可能拉低该线的器件在所选 VOL 上限、供电和温度条件下确认的能力；应按最弱保证约束，不拿 MCU 的绝对最大电流、典型值或某个最强 target 代替。读 ACK 的 target、读数据的 target、会拉伸 SCL 的 target 都不能遗漏。多个已有上拉并联时先算等效 R，不能只看新加的电阻标签。

若标称电阻容差为 ±e，要满足整个容差范围：R_nominal_min=R_actual_min/(1−e)，R_nominal_max=R_actual_max/(1+e)。前者用最小实际电阻检查吸电流/最短上升，后者用最大实际电阻检查最长上升。下界高于上界时无解；“选中间值”并不存在。

原创有解例，Fast-mode：VDD_max=3.465 V、VOL_max=0.4 V、IOL=3 mA、Cb∈[80,120] pF、tr∈[20,300] ns、e=5%。

- R_sink_min≈1021.67 Ω，R_rise_min≈295.05 Ω，因此实际下界≈1021.67 Ω。
- 实际上界≈2950.55 Ω，标称可行区间约 [1075.44,2810.05] Ω。
- 标称 2.2 kΩ 的最小实际值 2090 Ω：按所选 VOL 边界估算吸电流约 1.467 mA。
- 最大实际值 2310 Ω、最大 Cb=120 pF 时 tr≈234.872 ns；最小实际值和 Cb=80 pF 时 tr≈141.669 ns，均在本计算约束内。
- 标称 1 kΩ 落在容差调整后的下界之外；标称 3.3 kΩ 落在上界之外。

释放到达到 70% 的时间不等于 tr。用无容差 2.2 kΩ、120 pF 的同一理想 RC 算，30%→70% 为 223.687 ns，而从 0→70% 约为 317.849 ns。控制器“释放 SDA/SCL 后等 300 ns”的正确性要看从哪个阈值、初始电压和边沿起算，不能直接拿最大 tr 当所有软件等待时间。

原创无解例：把低电平限值锁定为 0.4 V，只确认 3 mA 吸电流能力，VDD_max=5.5 V、Cb=400 pF、tr_max=300 ns、无电阻容差时，下界为 1700 Ω，上界约 885.16 Ω。换 1 kΩ 会违背当前低电平能力约束，换 2.2 kΩ 会违背上升时间。应该修改电容/速度等级/驱动或总线分段方案，并重新核对全部条件，不继续猜电阻。

Table 10 注 [4] 还讨论 Fast-mode 满载 400 pF、400 kHz 的 6 mA/0.6 V 条件。不能把另一个 VOL/电流工作点悄悄替入本例的 0.4 V/3 mA 合同；若所选器件确有更高驱动保证，重新检查所有接收阈值与电平约束后才能重新求区间。[UM10204 Rev.7.0，Table 10、§7.2](https://www.nxp.com/docs/en/user-guide/UM10204.pdf#page=43)

边界例：VDD_max=3.4 V、VOL_max=0.4 V、3 mA、100 pF、tr_max=84.73 ns、没有最小 tr 约束与容差，则本模型的上下界恰好都是 1000 Ω。1000 Ω 被接受，999.999 Ω 与 1000.001 Ω 被拒绝；加 1% 容差就无解。这里只是展示闭区间与边界测试，不是给真实设计推荐零裕量。模型用有理数把已四舍五入的 0.8473 当精确系数，避免二进制浮点误判单点；真实 RC、阈值和材料不具备这种精确性。

区间检查不包括漏电造成的最终高电平下降、VOL 对电流的真实曲线、分布参数、跨电源域、缓冲器偏置、并联器件漏电、断电钳位、串联保护电阻和噪声。电容只是估算时，也不能凭“算出来有区间”宣称板子通过；必须继续核对各器件资料和测量。

### 五 有界 bus-clear 是一个失败也能结束的状态机

先确认自己拥有恢复权限：停止新事务，使正在运行的传输收敛，确认没有另一个 controller 的合法占用；按照目标适配器规则接管引脚。只有 SCL/SDA 低，不能据此证明总线故障或安全可抢占。本页只在独占、开漏前提下建模，不操作真实 GPIO，也不关闭真实外设。

NXP 对 SCL 卡低优先给出硬件复位、无复位输入时电源循环的路径；对 SDA 卡低给出九个时钟，仍未释放再转硬件复位/电源循环。[UM10204 Rev.7.0，§3.1.16](https://www.nxp.com/docs/en/user-guide/UM10204.pdf#page=19)

下面是原创课堂策略：最多九次清理循环，观察释放后转一次 STOP，再检查空闲；提前结束、整次期限、STOP 与 tBUF 检查是这里明确添加的工程合同，不冒称为规范原文。是否允许提前结束、引脚交接怎样执行以及后续复位都需要目标设备/适配器批准。I²C 的这段规范没有为本页定义一个通用毫秒级拉伸超时；本模型的预算由课堂调用方指定，不套用 SMBus 的超时。

| 状态 | 本模型的动作与退出 |
|---|---|
| 拒绝恢复 | 不独占或不是开漏配置，返回 REFUSED，不生成边沿 |
| 初始观察 | 释放两线，限时等实际 SCL 高；SDA 已高则只做有界空闲检查 |
| 清理低段 | SDA 保持释放；拉低 SCL，保持低段预算 |
| 清理高段 | 释放 SCL，限时等实际高；卡低时返回 SCL_TIMEOUT，不算有效清理沿 |
| 完成清理循环 | 保持高段后完成计数；脚本在低阶段允许 target 释放 SDA，避免把它当数据在高段改变 |
| 九次仍卡低 | 返回 SDA_STUCK；不继续第十次清理、不无限重试 |
| STOP 尝试 | 低 SCL 下拉 SDA；释放 SCL并限时确认高；保持 STOP 建立时间后释放 SDA |
| STOP 检查 | SDA 仍低为 STOP_FAILED；不能只凭“调用了 STOP 函数”报成功 |
| 空闲检查 | 两线保持高达到配置的窗口；本故障模型可注入 SDA 再卡低，返回 BUS_NOT_IDLE |
| 整次期限 | 任何等待/保持会到达整体 deadline，则返回 DEADLINE；最后释放控制器两线 |

清理脉冲数与全部 SCL 边沿数分开：本策略在 SDA 于低段确认释放后，为合法 STOP 还要一次 SCL 上升，单独标为 `stop-scl-high`。九次清理后成功的轨迹可能有十个实际上升沿，最后一个属于 STOP 准备，不伪称“总共只有九个引脚上升沿”。SDA 始终未释放的九次失败轨迹在最后高段退出，清理时已经释放 SCL，失败 cleanup 不增加第十个清理沿。中途期限到达可能留下未完成高/低段，结果同时保留实际有效沿和完成循环计数。

主机状态机中的每个量都是合成 tick。默认 low=5、high=5、单次等待 SCL=10、STOP 建立=5、空闲观察=5、整次预算=200。tick 不等于 μs，不是可照搬到任意 MCU 的参数。有效观察必须严格早于局部/整体期限：SCL 在第 9 tick 变高可接受，在第 10 tick 才变高按当前等待合同返回超时；成功需要最后空闲观察也在整体期限前。

无拉伸的有限轨迹，结果可独立算出：

- 起初两线空闲：观察 5 tick，ALREADY_IDLE，0 次清理。
- 第三次清理后 SDA 释放：3×(5+5)+STOP 低段 5+建立 5+空闲 5=45 tick，RECOVERED。
- SCL 起初永远低：10 tick，SCL_TIMEOUT，0 个有效清理上升沿。
- 第一轮完成、第二轮释放 SCL 后永远低：10+5+10=25 tick，SCL_TIMEOUT，只完成 1 次清理。
- SDA 九次后仍低：9×10=90 tick，SDA_STUCK。
- 第三次释放后、STOP 又被 target 拉低：30+5+5=40 tick，STOP_FAILED。
- 第三次释放后，空闲窗口第 2 tick SDA 再卡低：42 tick，BUS_NOT_IDLE。

真实实现还必须为计时、引脚访问、外设停机/恢复和调度提供实际有界保证；“外层 while 有 deadline”不能救一个永远不返回的底层回调。故障返回后保留原因，重新核对控制器状态和设备协议；不要自动再执行可能已经部分生效的写事务。硬件复位、电源循环会影响共享设备与状态，本实验不执行，也不能把九钟恢复成功当成业务事务成功。

## 常见误区与失败边界

- 最后读 NACK 是错误告警：它在本事务中是正常结束；地址写/读阶段的 NACK 才需要按具体原因处理。
- 忽略第九钟下降：ACK 方可能还在持有 SDA；方向交接与 Sr/STOP 都需要正确衔接。
- SDA 释放就立刻算高：数据建立必须按真实 RC 和阈值验证，数字 trace 没有证明它。
- 降低 fSCL 就能继续声称 Fast-mode 的 300 ns 合规：换速度/模式需重新定义合同；仍声称同一模式时，适用的 rise time 约束不会凭频率设置自动消失。
- 只有 MCU 会拉低：target 的 ACK、读数据和 SCL 拉伸能力同样进入下界。
- 把多个 2.2 kΩ 忽略并联：三只并联约 733.33 Ω，可能已在本例吸电流下界之外。
- 九次循环都写了“释放 SCL”就算九钟：必须观察到真实高；短路/合法拉伸不能被软件动作名掩盖。
- 打九钟一定治好：时钟卡低、硬件短路、掉电钳位、设备状态异常都可能需要不同处理。

## 面试追问

1. 为什么 30%→70% 的 tr 不能直接当释放到高电平的延时？答到阈值起点、初始电压和 RC 系数差异，再说控制器实际如何计时。
2. 为什么更小上拉不总是更好？同时讲吸电流、VOL、功耗、Fast-mode 最小 tr 与容差；不要只回答“上升快”。
3. 上下界相交但只剩一个点，能不能量产？数学模型可以有闭区间单点；真实设计还要元件、温度、电容估计、阈值与测量裕量，不能从主机接受推导量产合格。
4. SDA 低但 SCL 高能立刻开始恢复吗？先确认事务拥有者和合法占用；低电平不是故障诊断的充分证据。
5. 为什么恢复成功仍不能报告写事务成功？恢复只证明当前模型观察到的空闲及退出条件，未证明此前写入的完整性、设备内部执行或幂等性。

可运行文件：[原创主机模型](../../examples/python/i2c_timing_recovery.py)、[边界与故障测试](../../tests/host_i2c_timing_recovery_test.py)。从仓库根目录运行，Python 3.10+、只用标准库：

```bash
PYTHONDONTWRITEBYTECODE=1 python3 examples/python/i2c_timing_recovery.py
PYTHONDONTWRITEBYTECODE=1 python3 tests/host_i2c_timing_recovery_test.py
```

验收不是打印 PASS 就结束：

1. 从 DATA_RISE 重新解码出 0xA0、0x12、0xA1、0xA5、0x3C；证明 target/controller 的 ACK 方和最后双释放 NACK；检查 45 个采样钟及 Sr/STOP 的单独边沿。
2. 对 2.2 kΩ 两个容差端分别算吸电流和 rise time；再制造无解、单点和比边界大/小 0.001 Ω 的输入。测试把 Fast-mode 20 ns 最小 tr 作为独立约束，不能遗漏。
3. 对起初空闲、1–9 次后释放、SCL 初始/中途/STOP 超时、九次 SDA 卡低、STOP 失败、空闲窗口再卡低逐条检查退出原因。REFUSED 不得生成边沿，任何失败都不得强推高。
4. 用整体预算逐 tick 截断 LOW/HIGH/STOP/空闲阶段；检查计时单调、整体不越界、最多 9 个有效清理沿、最多 1 个未完成清理循环以及失败 cleanup 释放引脚。
