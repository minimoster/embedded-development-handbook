# TCP Reno 与 RTO · 从累计 ACK 手推一次有限恢复

学习优先级：P2，可选补充。先读 [PR06 字节流](pr06.md)、[PR07 TCP 连接](pr07.md)、[PR08 业务重试](pr08.md) 与 [PR12 流控/拥塞控制](pr12.md)。本页只讨论发送侧的拥塞窗口和重传计时，不重写 socket 接口、应用帧或业务幂等。

正文、事件表和 [Python 状态模型](../../examples/python/tcp_reno_rto.py) 为原创教学内容；[主机测试](../../tests/host_tcp_reno_rto_test.py) 已在 Python 3.12.14 运行。所有 ACK、丢失假设和时间都是合成输入；没有执行 Linux 内核、真实网络、抓包或目标板实验，也没有复制 Linux TCP 实现。本模型不是协议栈、网络模拟器或 RFC 符合性认证。

## 直接回答

发送新数据同时受 `cwnd` 和接收方通告窗口 `rwnd` 约束；累计 ACK 推进最老未确认字节 `SND.UNA`。经典 Reno 在第三个合格重复 ACK 上快重传并进入快恢复；RTO 到期则重传最老未确认段、把窗口退到一个 SMSS，并对等待时间退避。两条恢复路径不能混为一条“丢包后窗口减半”。ACK 数值、在途字节数、拥塞状态和计时器要分别记录，才能解释每一步。[RFC 9293 §3.4](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.4)、[RFC 5681 §2–3](https://www.rfc-editor.org/rfc/rfc5681.html#section-2)、[RFC 6298 §5](https://www.rfc-editor.org/rfc/rfc6298.html#section-5)

## 原理拆解

### 一 先把模型边界写清楚

选定已建立连接的一个发送方向；不模拟握手、关闭、IP、校验和或接收端实现。所有序号是握手后数据的相对字节偏移，首字节记作 0，不代表在线路上宣告 ISN=0。一个段恰好携带 `SMSS=1000 byte`，没有 TCP/IP 首部字节混进这个数。

| 模型选择 | 为什么要明示 |
|---|---|
| 累计 ACK；无 SACK、无 timestamp option | 不能由 ACK 定位所有收到的乱序段；重传 ACK 的 RTT 有歧义 |
| 主轨迹每批原始数据仅一个缺口 | 便于手推 Reno；同一缺口的重传还可能再次丢失，RTO 轨迹允许这种重复失败 |
| 固定 `rwnd=64000 byte`，全长段、ACK 在段边界上 | 不处理窗口更新、零窗口探测、部分段 ACK、PMTU/MSS 变化 |
| `cwnd==ssthresh` 时选拥塞避免 | 这是 RFC 5681 允许的选择；不能说相等时只有一种合法行为 |
| 拥塞避免采用每个新 ACK 的字节公式并整数取整 | 不实现另一种累计已确认字节计数法；延迟 ACK 的增长可能更慢 |
| 不实现 Limited Transmit | 第一、第二个重复 ACK 不自动发送额外数据；因此不是 RFC 5681 全功能实现 |
| 不实现 NewReno、PRR、RACK/TLP、ECN、CUBIC/BBR、pacing | 这些名字不能当作本实验已覆盖的功能；更不代表 Linux 默认配置 |
| 时间是精确有理数秒；调用者显式派发到期事件 | 无线程、系统时钟或包队列；同一时刻 ACK/到期的顺序由场景指定 |
| 不允许序号回绕 | 真 TCP 是模 `2^32` 的序号空间，本代码故意拒绝到达回绕边界 |

构造参数 `cwnd` 表示场景开始时的已建立连接状态。恢复轨迹从 `cwnd=6000` 开始，是暖状态，并非推荐六段初始窗口。正常轨迹从两段开始，也不声称所有 TCP 都必须从两段开始。`ssthresh=4000/8000` 是方便观察转折的课堂输入，不是路径容量的测量结果。RFC 5681 的 IW 规则与部署中的其他初始窗口方案需另外核对。[RFC 5681 §3.1](https://www.rfc-editor.org/rfc/rfc5681.html#section-3.1)

### 二 ACK 指向下一字节，FlightSize 不是 cwnd

发送区间 `[0,1000)` 与 `[1000,2000)` 后，`SND.NXT=2000`。收到 `ACK=1000` 表示序号小于 1000 的字节已被累计确认，下一期待字节是 1000；不表示“编号为 1000 的字节也已收到”。在本模型未回绕、没有 SYN/FIN 的条件下：

```text
FlightSize = SND.NXT - SND.UNA
新数据额度 = max(0, min(cwnd, rwnd) - FlightSize)
合法新 ACK: SND.UNA < ACK <= SND.NXT
```

`FlightSize` 是已发但尚未累计确认的字节数，可能包含接收端已经缓存的乱序数据。因此它不是“当前仍在网线上飞行的物理字节”的测量值。重传相同区间不推进 `SND.NXT`，也不把 `FlightSize` 再加一遍；快恢复的窗口膨胀更不会神奇地把未确认字节减掉。[RFC 5681 §2](https://www.rfc-editor.org/rfc/rfc5681.html#section-2)

原创反例：`cwnd=12000`、应用只发 6000、接收窗口足够，丢失发生时 `FlightSize=6000`。本模型设置 `ssthresh=max(6000/2,2000)=3000`，不是 6000。RFC 给的是相应减小阈值的上界，本实验选择恰好等于该上界，不把“至多”改成“任何实现都必须恰好”。即使以后 `FlightSize>cwnd`，也只是暂时没有新数据额度，不意味着必须收回已在途数据。[RFC 5681 §3.1 式(4)](https://www.rfc-editor.org/rfc/rfc5681.html#section-3.1)

### 三 慢启动与拥塞避免由新 ACK 驱动

设一个 ACK 新确认 `N` 字节。课堂选择：

```text
若 cwnd < ssthresh: cwnd += min(N, SMSS)
否则:              cwnd += max(1, floor(SMSS*SMSS/cwnd))
```

前一条对应慢启动的按 ACK 增长；后一条选用 RFC 5681 的可接受近似字节公式，而非推荐的累计字节计数实现。整数结果为零时取一个字节，避免窗口停止增长。本页只用这些有限场景解释增长，不证明任意 ACK 策略下的吞吐、公平性或每 RTT 上界。[RFC 5681 §3.1 式(2)–(3)](https://www.rfc-editor.org/rfc/rfc5681.html#section-3.1)

“慢启动指数、拥塞避免线性”描述的是特定 ACK/持续发送条件下每轮 RTT 的大致趋势，不能当作收到一个 ACK 就翻倍或每个 ACK 增加一个 SMSS。若 `cwnd=4000` 的四段被一个累计 ACK 一次确认，慢启动只加 1000；本页拥塞避免公式只加 `floor(1000000/4000)=250`。ACK 汇聚/延迟会改变增长，Reno 不由应用的一次 send 调用直接涨窗口。

### 四 相同 ACK 号还不足以叫合格重复 ACK

本页讨论 RFC 5681 非 SACK 的判据：仍有未确认数据、ACK 不携带数据、SYN/FIN 关闭、ACK 号等于当前最大的累计 ACK、通告窗口和上一 ACK 相同。窗口更新即使 ACK 号没变，也不能仅凭这个号增加重复 ACK 计数。旧 ACK 小于当前 `SND.UNA` 也不是本计数器的新证据；全部数据已确认后的相同 ACK 不触发快重传。[RFC 5681 §2](https://www.rfc-editor.org/rfc/rfc5681.html#section-2)

接口 `ack(number, now, ...)` 只接收已建立状态的纯 ACK；窗口变化、携带数据、SYN/FIN 被拒绝为“超出模型”，状态保持原样。这不表示真实 TCP 可以把这些合法网络事件都当坏包丢掉；只表示我们没有模拟它们。旧 ACK 和无在途数据的 ACK 有独立返回结果。重复 ACK 可以由乱序、复制或丢失引起，三个也不是数学证明“网络必定丢了哪一包”。本实验不提供防伪 ACK 或乱序判别机制。

### 五 三个重复 ACK 后的窗口要先膨胀，再收缩

本模型第一个、第二个重复 ACK 只计数。第三个触发：用当前 `FlightSize` 算 `ssthresh`；重传 `SND.UNA` 开始的段；设置 `cwnd=ssthresh+3*SMSS`。以后每个额外重复 ACK 再加一个 SMSS。收到第一个推进 `SND.UNA` 的 ACK 时，经典 Reno 把 `cwnd` 收到 `ssthresh` 并退出快恢复，本实验不在同一个 ACK 上再叠加一次慢启动或拥塞避免增长。[RFC 5681 §3.2](https://www.rfc-editor.org/rfc/rfc5681.html#section-3.2)

人工膨胀表达的是 ACK 时钟仍有进展的恢复策略，不是容量忽然增加。发送新段仍要检查接收窗口与现有 Flight；`ack()` 本身不自动调用 `send()`，调用方才能决定是否还有待发应用数据。多丢失时，首个新 ACK 可能只填部分缺口，Reno 仍会退出；本测试验证这个有限边界，但不补成 NewReno 多缺口算法。主完整恢复轨迹只注入一个缺口，接收方缓存后继五段。

### 六 RTO 是估计加余量，不等于 RTT

选定 `G=0.001 s`、初始 RTO 为 1 s、最小 RTO 为 1 s、最大为 60 s；上限是本实验选值，并非全平台固定常量。没有握手事件，因此没有演示 SYN 超时后的特殊重置。[RFC 6298 §2、§5.7](https://www.rfc-editor.org/rfc/rfc6298.html#section-2)

```text
首个可用样本 R: SRTT=R, RTTVAR=R/2
后续样本 R':    RTTVAR=(3/4)*旧RTTVAR + (1/4)*abs(旧SRTT-R')
                SRTT=(7/8)*旧SRTT + (1/8)*R'
raw_RTO = SRTT + max(G, 4*RTTVAR)
本实验 RTO = min(60, max(1, raw_RTO))  单位：秒
```

先更新 RTTVAR，再更新 SRTT；差值要用旧 SRTT。手推检查：首样本 1 s 得 `SRTT=1, RTTVAR=0.5, RTO=3`；下个样本 3 s 得 `RTTVAR=0.875, SRTT=1.25, RTO=4.75`。若误用更新后的 SRTT 计算差值，测试中的 0.875 会错掉。正常轨迹的首样本 0.2 s 得原始 RTO=0.6 s，经本实验下限变为 1 s。下限不是把实际 RTT改成1秒。[RFC 6298 §2.2–2.4、§4](https://www.rfc-editor.org/rfc/rfc6298.html#section-2)

### 七 一个数据重传计时器怎样管理

这里用一个重传计时器，而非每发一段各开一个独立闹钟。首次发送而计时器未运行时，设 `deadline=now+RTO`；发送后续新段不重置现有期限。新 ACK 推进累计确认后，若还有未确认段，就以当前 RTO 从 ACK 时刻重新计时；全部确认则关闭。普通重复 ACK 不续命。[RFC 6298 §5.1–5.3](https://www.rfc-editor.org/rfc/rfc6298.html#section-5)

RTO 到期时，本模型只重传最老未确认段；若这个段此前未通过 RTO 重传，就重算 `ssthresh=max(floor(FlightSize/2),2*SMSS)`，如果同一段已通过 RTO 重传则保持阈值；`cwnd=SMSS`，退出快恢复并清计数。然后 `RTO=min(60,2*RTO)`，用新的等待时间重新设期限。减小窗口和计时退避是两套同时变化的状态，不能互相替代。[RFC 5681 §3.1](https://www.rfc-editor.org/rfc/rfc5681.html#section-3.1)、[RFC 6298 §5.4–5.6](https://www.rfc-editor.org/rfc/rfc6298.html#section-5)

快重传可以早于 RTO。课堂实现快重传时另把计时器保护到 `now+当前RTO`，避免旧期限导致同一段紧接着被 RTO 过早重传；这是本模型明确的计时选择，不是“所有重复 ACK 都重启 RTO”。到期接口还检查距该段上一发送至少经过一个当前 RTO。正常事件不得跨过已过期的期限而省掉到期派发；恰好等于期限时允许调用方明确选择 ACK 先或到期先。这些合成事件调度约束不声称复刻内核竞态。[RFC 6298 §5 的避免过早重传要求](https://www.rfc-editor.org/rfc/rfc6298.html#section-5)

### 八 Karn：收到 ACK 不自动解除重传歧义

若 0 秒发一段，1 秒重传，1.2 秒收到 ACK，不能直接确定 RTT 是 1.2 秒还是 0.2 秒。无 timestamp option 时不能从重传段取得 RTT 样本；不能因为 ACK 数字推进、或者一个累计 ACK 也覆盖未重传的后继数据，就把它随便算进估计器。[RFC 6298 §3](https://www.rfc-editor.org/rfc/rfc6298.html#section-3)

实现只保留一个待测新段的 `(end, sent_at)`。任何重传都清除待测样本，并保守禁止新探针，直至当次重传时所有已发数据被累计确认。恢复期发送的新数据也不建立探针；解除禁止后，再发送未重传的新数据才可测。这比“只检查某一段的重传位”更保守，可能少取样；它是为避免本课堂累计 ACK 歧义而选择的边界，不是完整 TCP 的样本调度设计。协议栈还需满足其采样要求和 timestamp 规则。

因此恢复 ACK 可以关闭计时器，却仍保留退避后的 RTO。后来明确的干净样本才重新计算它，可能让 RTO 收敛；不要在任意新 ACK 上直接清除退避。模型选择保留旧 SRTT/RTTVAR，不实现反复退避后丢弃估计的可选策略。[RFC 6298 §5 末尾说明](https://www.rfc-editor.org/rfc/rfc6298.html#section-5)、[RFC 9293 §3.8.1–3.8.2](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.8.1)

## 例子与推演

以下表全是手推后由主机状态模型重放的合成轨迹。所有窗口、Flight 和 ACK 单位是 byte；时间与 RTO 单位是秒；表中状态均为事件处理之后。`off` 表示无未确认数据时关闭计时器。发送事件的段数不会替代 ACK 的字节编号。

### 轨迹 A：两段起步，走到拥塞避免

起始 `cwnd=2000, ssthresh=4000`。代码调用和每步结果：

| t | 事件 | UNA / NXT | Flight | cwnd | ssthresh | RTO / deadline |
|---|---|---|---:|---:|---:|---|
| 0 | 发 2 段 | 0 / 2000 | 2000 | 2000 | 4000 | 1 / 1 |
| 0.20 | ACK 1000 | 1000 / 2000 | 1000 | 3000 | 4000 | 1 / 1.20 |
| 0.21 | ACK 2000 | 2000 / 2000 | 0 | 4000 | 4000 | 1 / off |
| 0.22 | 发 4 段 | 2000 / 6000 | 4000 | 4000 | 4000 | 1 / 1.22 |
| 0.42 | ACK 3000 | 3000 / 6000 | 3000 | 4250 | 4000 | 1 / 1.42 |
| 0.43 | ACK 4000 | 4000 / 6000 | 2000 | 4485 | 4000 | 1 / 1.43 |
| 0.44 | ACK 5000 | 5000 / 6000 | 1000 | 4707 | 4000 | 1 / 1.44 |
| 0.45 | ACK 6000 | 6000 / 6000 | 0 | 4919 | 4000 | 1 / off |

0.21 秒只是到达阈值，下一新 ACK 才用拥塞避免式；四次整数增量分别是 250、235、222、212。首个 0.20 秒样本初始化估计；0.42 秒的探针来自 0.22 秒发送，仍为 0.20 秒，使 RTTVAR 从 0.1 降到 0.075。本实验只在新发送时安排一个探针，不把表中每行 ACK 都算新 RTT。

### 轨迹 B：一个缺口，五个重复 ACK，Reno 快恢复

起始暖状态 `cwnd=6000, ssthresh=8000`。一次发 `[0,6000)` 六段，设 `[0,1000)` 丢失，后继段先后到达并被接收方缓存；每个合格 ACK 仍期待字节 0。没有应用待发新数据，因此没注入额外发送。

| t | 事件 | UNA / NXT | Flight | dupACK | cwnd | ssthresh | RTO / deadline |
|---|---|---|---:|---:|---:|---:|---|
| 0 | 发 6 段 | 0 / 6000 | 6000 | 0 | 6000 | 8000 | 1 / 1 |
| 0.1 | ACK 0，第一个重复 | 0 / 6000 | 6000 | 1 | 6000 | 8000 | 1 / 1 |
| 0.2 | ACK 0，第二个重复 | 0 / 6000 | 6000 | 2 | 6000 | 8000 | 1 / 1 |
| 0.3 | ACK 0，第三个，重传 `[0,1000)` | 0 / 6000 | 6000 | 3 | 6000 | 3000 | 1 / 1.3 |
| 0.4 | ACK 0，第四个 | 0 / 6000 | 6000 | 4 | 7000 | 3000 | 1 / 1.3 |
| 0.5 | ACK 0，第五个 | 0 / 6000 | 6000 | 5 | 8000 | 3000 | 1 / 1.3 |
| 0.6 | ACK 6000，完整填洞并退出恢复 | 6000 / 6000 | 0 | 0 | 3000 | 3000 | 1 / off |

0.3 秒 `ssthresh=6000/2=3000`，`cwnd=3000+3000=6000`；此刻窗口数值没变，恢复状态却变了。0.6 秒收缩到 3000，不能因为 ACK 一次确认 6000 就再加六个 SMSS。由于 `[0,1000)` 被重传，待测探针被清除；本轨迹没有干净 RTT 样本，`SRTT` 仍未初始化。要观察恢复期间的新发送，可运行测试中额外两段与累计 ACK 8000 的场景；它也不产生歧义样本。

### 轨迹 C：缺口没获得足够重复 ACK，连续 RTO 后才恢复

同样从六段暖状态开始；合成场景只把最老段的累计确认留住，并且第一次重传也未得到及时确认。不能靠发送方知道接收端到底缓存了什么。

| t | 事件 | UNA / NXT | Flight | cwnd | ssthresh | RTO / deadline |
|---|---|---|---:|---:|---:|---|
| 0 | 发 6 段 | 0 / 6000 | 6000 | 6000 | 8000 | 1 / 1 |
| 1 | 到期，首次 RTO 重传 `[0,1000)` | 0 / 6000 | 6000 | 1000 | 3000 | 2 / 3 |
| 3 | 到期，同段再次 RTO 重传 | 0 / 6000 | 6000 | 1000 | 3000 | 4 / 7 |
| 3.2 | ACK 6000，恢复数据被累计确认 | 6000 / 6000 | 0 | 2000 | 3000 | 4 / off |
| 3.3 | 发 2 段新数据 `[6000,8000)` | 6000 / 8000 | 2000 | 2000 | 3000 | 4 / 7.3 |
| 3.5 | ACK 7000，干净样本 0.2 s | 7000 / 8000 | 1000 | 3000 | 3000 | 1 / 4.5 |
| 3.51 | ACK 8000 | 8000 / 8000 | 0 | 3333 | 3000 | 1 / off |

第二次到期保持 `ssthresh=3000`，并非把 3000 再减成 1500。3.2 秒虽有进展，Karn 禁止把它当样本，RTO 仍为 4；3.5 秒的新数据未重传，才能计算新 RTO。此时慢启动只增一次到 3000；3.51 秒转用拥塞避免，加 333。

测试还用十段/局部 ACK 验证更细的区别：一个段首次到期算阈值；它被确认后，下一个最老段的首次 RTO 可以按新的 Flight 重算；该新段以后再到期则保持。规则跟随“这个段是否已通过 RTO 重传”，不是整条连接永远只能改一次阈值。

## 常见误区与失败边界

- “重复 ACK 三次就把 cwnd 直接减半”：漏了基于 Flight 的阈值、人工膨胀以及恢复 ACK 时的收缩。
- “重传了一段，所以在途字节翻倍”：重传的是相同序号区间；本模型不会推进 NXT，实际线路开销与逻辑 Flight 要分别统计。
- “任意 ACK 让 RTO 归零/重置到最小值”：普通重复 ACK 不重启期限；恢复 ACK 本身不消除 RTT 歧义；无在途数据只关闭计时器。
- “RTO 从 1 到 2 到 4，因此到期点在 1、2、4”：表 C 的到期点是累计等待后的 1、3、7。上限 60 后也要从当前时刻再等 60；模型没有实现连接失败阈值和应用总期限。
- “这里调了一个 Reno class，所以 Linux 和板上网络已验证”：代码没有 socket、真实包或操作系统 TCP 状态；它只验证作者选定的事件转换。
- 多缺口、ACK 丢失/复制、严重乱序、ACK 攻击、序号回绕与零窗口都需要更多状态。测试中的局部恢复 ACK 只检查经典 Reno 的退出选择，不能据此宣称恢复效率好。
- RFC 5681 对超时恢复诱发的某些重复 ACK 处理保留实现差异。本模型仍按课堂重复 ACK 计数规则处理，没有主张覆盖真实协议栈的所有混合恢复情况。

## 面试追问

1. `cwnd=12000, Flight=6000, SMSS=1000` 时第三个重复 ACK 后是什么？答：本模型阈值 3000，窗口 6000；不是阈值 6000。若已有三段而非六段，阈值有 2000 的下限。
2. 第四、第五个重复 ACK 明明提示接收方又收到数据，为何 Flight 没减少？答：累计确认左边界还没推进；乱序已收到字节仍在逻辑 Flight 中。
3. ACK 号相同但窗口变化，为何不能加计数？答：非 SACK 重复 ACK 定义还要求窗口不变；它可能只是窗口更新。
4. 何时退避 RTO 才会收敛？答：先排除重传歧义，再有明确的新数据 RTT 样本；仅 ACK 推进或关闭计时器不足以确定新估计。
5. 第一个推进 ACK 只填部分洞怎么办？答：经典 Reno 退出快恢复，效率可能差；本模型不做 NewReno，不能假装所有丢包组合都已解决。
