# PR09 · CRC、checksum、MAC 和签名怎么区分？

学习优先级：P1。先独立回答，再展开机制与验证。

## 直接回答

CRC/普通 checksum 用于检测某些传输或存储错误，不提供对抗攻击的真实性。MAC 用共享秘密验证消息，数字签名用公私钥支持验证与来源约束。固件更新的安全性不能只用 CRC 声称。

## 原理拆解

CRC 的多项式、初值、位序、反射和最终异或都需固定，否则同称 CRC16 也可能不同。攻击者可重新计算 CRC；认证还应覆盖版本、设备适用性和防重放信息。密钥管理和信任根是系统设计的一部分。

TCP 的 checksum 不是 CRC。RFC 9293 定义的是覆盖 TCP 首部、数据及相应 IP 伪首部的16位反码校验和；它用于差错检测，不可当密码学认证。校验算法名称相同仍要核对覆盖范围与字节序。

## 例子与推演

同一帧用 CRC 可以发现噪声导致的损坏；OTA 包需要受信任签名验证，再执行版本/设备策略，写入非活动槽并校验。本文不设计自创密码算法。

## 常见误区与失败边界

“加密就一定认证”不成立，模式/协议可能没有完整性保障。不要把口令/API key 放公开仓库或日志，测试只用虚构数据。

## 面试追问

校验成功但解析仍崩溃为何？答：CRC 只检查完整性的一种条件，仍需长度、范围、格式与语义验证。

## 动手练习与验收

为协议列被验证的字节范围和算法参数；验收：损坏检测与恶意篡改分别建威胁模型，安全方案需专门审核。

## 来源与适用范围

- [C11 委员会草案 N1570（2011）](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)：公开草案，作为 C11 基线；不是最新版 C 标准。
- [IETF RFC 9293：TCP](https://www.rfc-editor.org/rfc/rfc9293.html)：2022 Internet Standard；TCP 是字节流。
