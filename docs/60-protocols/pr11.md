# PR11 · DNS、HTTP、HTTPS 与 TLS 握手怎样避免混说？

学习优先级：P0。先独立回答，再展开机制与验证。

## 直接回答

DNS把域名解析为相应记录；HTTP定义应用交互；HTTPS使用安全传输保护HTTP。TCP三次握手与TLS握手是不同层，TLS1.3有自己的消息/认证/密钥流程；现代HTTPS也不能一概假设传输都为TCP。

## 原理拆解

嵌入式TLS还依赖可信根、域名验证、时间、熵源、内存和版本策略。解析成功仅说明获取地址，不保证证书可信或应用请求成功。不要禁证书校验作为长期修复。

TLS1.3 的认证、密钥协商与记录加密是不同职责，不能套用“客户端用证书 RSA 公钥加密对称密钥发送”的旧式通用流程。证书公钥还可用于认证签名；算法协商不等于把协商结果写入证书。DNS 通用实现也需支持 UDP 和 TCP，不是只有区传才用 TCP。HTTP 方法与消息定界详见 [PR13](pr13.md)。

## 例子与推演

常见HTTP over TLS over TCP路径：解析域名→连接TCP→TLS校验/建立安全会话→发HTTP→解析响应。日志分别标阶段和错误；HTTP keep-alive与TCP keepalive不是同一配置。

## 常见误区与失败边界

“HTTPS三次握手”错误。“有锁图标就业务一定正确”忽略服务权限和数据语义。测试证书与私钥不能混入公共repo。

## 面试追问

板上TLS总失败、主机正常先查什么？答：时间、根证书、SNI/域名、版本/算法、内存与熵，不先绕安全警告。

## 动手练习与验收

画阶段时间线并注入DNS失败/证书不匹配/应用500。验收：故障分别报告，安全校验保持，不编造真实联网成功。

## 来源与适用范围

- [IETF RFC 1034：DNS Concepts](https://www.rfc-editor.org/rfc/rfc1034.html)：DNS 基础，现代扩展另查对应 RFC。
- [IETF RFC 8446：TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446.html)：2018；本页只限定 TLS1.3 基础，不描述所有 HTTPS 传输为 TCP。
- [IETF RFC 9293：TCP](https://www.rfc-editor.org/rfc/rfc9293.html)：2022 Internet Standard；TCP 是字节流。

正文与例子为本仓库原创教学内容。来源用于核对机制，不表示原作者为本仓库背书。
