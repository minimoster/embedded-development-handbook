# PR13 · HTTP 的方法语义、消息定界和重试怎样写对？

学习优先级：P0。先独立回答，再展开机制与验证。

## 直接回答

GET/POST 首先是应用方法语义，和固定 TCP 报文个数、2 KiB URL 上限、是否 TLS 加密没有一一对应关系。HTTP/1.1 消息要按方法、状态和定界规则解析；收到一次 read 或 EOF 不天然表示完整响应。幂等描述重复请求的预期服务器效果，不要求每次响应完全相同。

## 原理拆解

GET 请求目标资源的表示，POST 请求资源按自己的语义处理内容。GET 是安全/幂等方法；POST 不默认具有相同性质，但应用可设计去重协议。GET 的 URI 可能出现在日志/历史里，POST 的主体也可能被记录；两者传输保护都依赖 HTTPS 等安全通道。

HTTP/1.1 定界先考虑 HEAD 与无主体状态等特例，再处理 Transfer-Encoding/Content-Length 等规则。长度单位是 octet，不是中文字符数。chunked 是传输定界，不等于 gzip 内容压缩。对于同时含冲突定界字段的输入，简化嵌入式解析器应拒绝并关闭，避免与代理解析差异造成请求走私。

Expect: 100-continue 是可选握手机制，不是所有 POST 都先发 header 再等 100；TCP 可拆分/合并任何写入。HTTP/2 用二进制帧和并发 stream，HPACK 针对字段压缩，不能把它当 gzip 的替代内容压缩。

## 例子与推演

设备上传一次控制结果后超时，客户端只知道没收到响应，不知道服务端是否已处理。若对 POST 无条件重试，可能重复动作；设计业务请求 ID、服务端去重和可查询结果才可解决这个特定业务边界。

HTTP/1.1 响应声明 Content-Length: 8，读到 5 字节后连接断开，应报告不完整，不能返回“成功收到5字节”。HEAD 响应即使给出长度字段，也不能把它当后面必有同长度主体。

## 常见误区与失败边界

Host 是 HTTP/1.1 请求的要求，不是所有响应都必须携带。CONNECT 已有建立隧道的标准用途，不能写“保留将来使用”。HTTP 无状态不等于服务器不能维护会话或数据库状态。

响应长度、header 数量、累计 header/body 大小和等待时间要设预算；不接受一个 Content-Length 就无上限分配。HTTP/2 多路复用也不消除底层 TCP 丢包造成的传输阻塞。实现应优先使用维护中的合适库，教学小解析器不可当生产安全实现。

## 面试追问

问：幂等请求为何第二次可以返回不同结果？答：保证预期效果重复一致，不保证资源在两次之间不变或响应字节相同。
问：100 Continue 证明业务已执行吗？答：它是临时响应，不是最终业务成功。
问：半包怎么和 HTTP 定界联动？答：先累计/状态机解码，再按规则判断消息完整，而非按 recv 边界。

## 动手练习与验收

建立离线响应样本：HEAD+长度、204、定长分三次输入、chunked、主体截断、非法重复长度与冲突长度字段。给解析状态机喂任意切分，记录成功/拒绝/不完整结果。

验收：任意网络切分不改变同一合法消息的解析结果；不把 EOF 都判成功；畸形输入不越界或无限分配；重试策略明确。该练习不发送真实控制请求，不声称已完成 TLS 联网或安全审计。
