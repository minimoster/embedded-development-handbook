# DV12 · 设备号、cdev、sysfs、devtmpfs 与 /dev 怎样连起来？

学习优先级：P0。先独立回答，再展开机制与验证。

## 直接回答

字符设备号/dev_t 标识访问目标，cdev 把设备号范围和 file_operations 关联，设备模型注册负责生命周期、sysfs/事件等；/dev 节点的名字与设备号是用户态入口。register_chrdev 或 class_create 单独调用不保证出现可用节点。总线匹配/probe 与字符设备接口是两条可组合的维度，不是互斥分类。

## 原理拆解

先分配/注册设备号范围，再初始化并加入 cdev，确保被暴露的操作和状态已准备好。device/class 注册进入设备模型，带有效 devt 的设备在配置支持的系统可经 devtmpfs 生成节点，用户态设备管理还可处理权限与链接。没有相应自动链时，可在受控环境用 mknod 建立入口；它不会替你实现驱动。

open 的路径查找取得设备节点信息，VFS 将操作接到驱动的 file_operations，建立打开对象并返回 fd。设备可以被多个线程/进程访问，open/read/write/ioctl 不会凭空变成原子操作，驱动需实现锁、状态和访问约束。

platform/USB/PCI 等总线负责设备描述、枚举或匹配与 probe/remove；字符/块/网络等接口描述对上暴露方式。USB 网卡使用 USB 总线但通常是网络接口，不因“USB”自动变字符设备。mtd NAND 的常见原始访问也不能一律归普通块设备。

## 例子与推演

一个 platform 传感器驱动在 probe 拿到资源，然后为用户暴露一个字符接口。排障顺序：DT/匹配是否正确→probe 是否成功→设备号和 cdev 是否注册→设备模型是否带 devt→/dev 是否挂适用文件系统→权限是否允许→open/读操作是否正常。

如果手工 mknod 后 open 仍返回 ENODEV，说明节点名字存在不等于驱动实例存在。若只注册 cdev 没有对应设备模型链，也不能等待 udev 自动知道一切。

## 常见误区与失败边界

“register_chrdev 的 name 就是 /dev 文件名”混淆注册名和节点创建。“字符设备必须串行且不能 seek”“所有块设备只允许用户态512字节倍数”都不是通用 API 保证；具体接口与 direct I/O 约束需逐项核对。

接口一旦暴露就可能被并发调用，因此注册/失败回退顺序很重要。remove 先停新访问与异步事件，等待既有访问归还，再释放资源；devm 自动资源释放不等于正在执行的操作已安全结束。fops没有close成员；close路径可调用flush，而release在打开文件的最后一个引用释放时执行。dup/fork/mmap等引用可能延迟release，不应把每次关闭一个fd都当成释放每open上下文。

## 面试追问

问：一个驱动能同时是 platform 驱动和字符接口吗？答：可以，分别负责匹配生命周期和用户入口。
问：mknod 能修复 probe 失败吗？答：不能，它只创建带设备号的名字。
问：为什么 cdev_add 后仍看不到 /dev？答：节点创建依赖设备模型/文件系统/用户态管理链，逐段查证。

## 动手练习与验收

先只读绘制目标接口的设备号→cdev→fops 和 device→sysfs→devtmpfs/用户管理两条关系。用专用测试内核才创建实验驱动并检查注册失败、第二实例、并发 open 和移除。

验收分别保存 probe、注册、节点、权限、open 的证据；没有目标内核/BSP 时，本卡只是可执行的排障方案，不声称已编译或板测。与[DV01设备模型](dv01.md)、[DV03设备树](dv03.md)交叉学习，分别验证匹配、入口和生命期。
