# DV07 · 中断下半部、workqueue 与线程化 IRQ 怎么选？

学习优先级：P0。先独立回答，再展开机制与验证。

## 直接回答

顶半部应快速确认/处理必要硬件状态，把较长工作交给合适的下半部或线程上下文。普通 threaded workqueue 的工作线程可睡眠；现代 WQ_BH 工作在 softirq 上下文且不能睡眠。传统 softirq/tasklet 与线程化 IRQ 的语境、并发和配置不同，不能笼统说“下半部都能睡”。

## 原理拆解

异步转交会引入数据生命周期与取消责任。卸载前需停止新事件，再同步正在执行的处理并取消/排空工作，否则 work 引用已释放设备。过度转交也可形成队列积压，需背压与统计。

CPU同步异常（例如SVC）、由软件置pending的硬件中断与Linux softirq分别属于不同层次。“软件触发”并不一律异步，也不一律用户态到内核态。Cortex-M向量入口常为void(void)，Linux注册的IRQ回调却接受irq/dev_id并返回irqreturn_t；其函数签名由具体入口ABI/API决定。

## 例子与推演

ISR 读取必要状态、记录有限数据并安排 work；work 完成总线事务和用户通知。若每次 IRQ 都排入新任务却无合并/上限，设备高频触发会耗尽处理能力。

## 常见误区与失败边界

只关 IRQ 不保证已经运行的 work 结束。把所有硬件状态读取延迟至 work，可能错过必须及时清理或读取的事件。

cancel_work_sync 在没有竞态再入队时才保证工作既不pending也不执行；因此先切断/阻止新事件来源再同步。delayed_work 应用 cancel_delayed_work_sync 的相应契约。不要持有worker完成所需的锁去等待同步取消，否则可自造死锁。

## 面试追问

中断风暴怎么办？答：检查清状态/触发源、节流、屏蔽与恢复策略，同时保留诊断而非无限打印。

## 动手练习与验收

写一份移除时序：停止产生→同步 IRQ→取消 work→释放资源。验收：所有异步引用有清楚归还点，配置语境明确。
