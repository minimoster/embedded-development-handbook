# DV11 · RCU 为什么允许并发读写，旧对象什么时候能释放？

学习优先级：P1。先独立回答，再展开机制与验证。

## 直接回答

RCU 的关键是把更新后的移除与旧对象回收分开：发布新版本后，已有读者仍可能使用旧版本，必须等相关读侧临界区经过宽限期才能回收。它不是“读写互斥的读优先锁”。RCU 本身也不自动序列化所有写者或保证对象字段的任意复合更新原子性。

## 原理拆解

典型流程是创建并完整初始化新对象，用适用发布接口替换受保护指针；读者在规定读侧临界区内，通过适用解引用接口取得指针；更新者等待 synchronize_rcu 或安排 call_rcu 回调，再释放旧对象。宽限期关注此前可能持有旧引用的读者，不是等系统从此再也没有读者。

写者并发冲突仍需自己的互斥规则。只保护顶层指针不自动保护对象内可变字段；可以用不可变快照或其他锁维护状态。读侧临界区结束后还想保留对象，需额外生命周期机制，不能裸保存指针。

顺序锁以序列计数检查读期间有无写入并重试，不等于一般“写优先读写锁”。它对写侧串行化和指针生命周期有要求。RCU、seqlock、rwlock 应按数据访问和回收条件选择，不能按一句“读多用这个”直接替换。

## 例子与推演

驱动维护只读配置快照 A。worker R1 取得 A 后处理；更新线程发布 B；新读者 R2 取得 B。这时 R1 和更新过程可以重叠，A 不能立刻 free。等对应宽限期结束，才允许回收 A。

若更新者连续发布大量快照而宽限期变长，待回收对象积压会耗内存；需给更新速率/待回收量预算，异步回收并不是无限容量。

## 常见误区与失败边界

“写时先拷贝，然后指针更新即可立即释放旧对象”会导致 use-after-free。“RCU 不需要锁”遗漏写者序列化和非 RCU 字段保护。普通 RCU 与 SRCU 等变体的可阻塞边界不同，不能把所有读侧都当可睡眠。

内存屏障、编译器可见性和回收时间是不同问题。普通赋值/volatile 不能代替 rcu_assign_pointer/rcu_dereference 等 API 的契约。卸载中已安排的回调需要按目标内核API做同步。synchronize_rcu等待适用宽限期，不等于所有已安排的callback都已执行完；先停止产生新回调，再用rcu_barrier或相应RCU变体的barrier排空，之后才能卸载回调代码。

## 面试追问

问：宽限期为何不阻止新读者？答：新读者通过新发布指针进入，不应再取得已移除对象。
问：RCU 能替代互斥量吗？答：只能替代满足对应数据/生命周期条件的一部分读写模式。
问：读者看见旧配置是 bug 吗？答：若一致快照与业务时效约定允许，不是；版本与传播延迟须定义。

## 动手练习与验收

先画三个读者、两次更新的时间线，标每次取得指针、离开读侧和允许回收点。写出发布、访问、写者串行化和最终释放的规则，不运行内核模块就不把伪代码当已验证。

在专用内核测试环境才做并发更新/卸载与适用调试检查；验收无提前释放、无回调引用已卸载代码、积压受控。无法验证时可用 mutex 的简单正确实现作为工程起点，先量出是否真的需要 RCU。
