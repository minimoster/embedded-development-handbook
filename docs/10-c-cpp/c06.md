# C06 · 结构体对齐、padding 与网络序列化有什么关系？

学习优先级：P0。先独立回答，再展开机制与验证。

## 直接回答

结构体可能有成员间和末尾填充；sizeof、对齐及位域布局依 ABI 与实现。不要把内存中的 struct 直接当作稳定的线协议或 Flash 格式，应逐字段编码字节序和长度。

## 原理拆解

对齐服务于目标架构的访问要求和性能。packed 等扩展可能减少布局填充，却带来非对齐访问、别名和性能问题。结构体 padding 的字节不适合直接做逻辑相等或作为安全序列化输出。

union的sizeof既要容纳最大成员，也要满足整个union的对齐。比如某LP64 ABI下long占8且对齐8，int[5]占20，union大小需取24而非20；外层结构体继续按成员对齐，最后再计尾部padding。此处只演算所标ABI，不能把64位主机结果套到AAPCS32。位域的布局、分配单元和pack pragma也依实现，默认不用它们定义跨平台协议。

## 例子与推演

```c
#include <stdint.h>
uint16_t read_be16(const uint8_t *p) {
    return (uint16_t)(((uint16_t)p[0] << 8) | p[1]);
}
```
两个字节 0x12、0x34 明确得到 0x1234，不受主机端序影响；调用方需先保证至少两个可读字节。

## 常见误区与失败边界

强转 uint8_t* 为 uint32_t* 既可能违反对齐，也可能违反有效类型/别名规则。位域适合特定编译器约束下的内部表示，不是跨端协议规范。

C有效类型规则、C++对象生命周期与union活动成员不是“地址相同即可读”的规则。通过unsigned char查看对象表示与把字节缓冲强转成任意T*再访问不同。C++17在特定条件下复制平凡可复制类型的对象表示可用memcpy；不能因此对拥有资源的类或非活动union成员任意操作。跨端数据优先逐字段编码，浮点/union类型双关则须单独标明标准与实现前提。

## 面试追问

memcmp 两个字段相同的 struct 一定为 0 吗？答：padding 或对象表示可能不同；逐字段比较。

## 动手练习与验收

为一条带 version、length、payload 的消息定义线格式，手工列出字节序。验收：截短、未知版本、长度溢出都能在读字段前拒绝。
