# C21 · extern "C" 与 opaque handle 怎样建立可靠的 C/C++ 边界？

学习优先级：P0。语言基线：C11、C++17；以同一平台、匹配工具链的 ABI 为前提。

## 直接回答

extern "C" 指定语言链接，不把 C++ 函数体变成 C，也不会修复缺失定义、错误函数签名或不同ABI。可维护的边界还要规定数据布局、所有权、错误返回、回调上下文和异常传播。对外暴露 C 可理解的函数与不完整类型句柄，内部可以保留 C++ 类与RAII。创建和销毁应配对到同一个实现侧，异常转换成稳定错误码。

## 原理拆解

语言链接影响函数类型及外部名字链接规则；具体符号和调用约定仍属于目标 ABI。C++文件里调用 C 接口时，声明必须采用匹配的语言链接；C编译器又不理解 extern "C" 语法，所以共享头文件常由 __cplusplus 包住这一部分。编译失败、缺符号、重复定义、调用约定不匹配应分开诊断；BSS/数据段不是找不到函数符号的通用原因。

opaque handle 只让调用方知道“有这种对象”，不公开类布局、vptr、STL容器和内部资源。函数接受长度明确的字节缓冲区；返回的拥有/借用对象要标清释放方。不要让 C 侧 free 一个 C++侧new出的对象，也不要把 std::string 或抛出式错误跨给不理解该运行库的调用者。

C++异常必须在约定边界内收敛。仅把 C导出函数标为 noexcept，未捕获异常会 terminate，不自动变错误码。异常关闭项目需另一个显式失败接口及对应实现，不能编译 -fno-exceptions 后还保留 throw/catch 源码。C++ RTTI和虚派发能否使用、静态初始化和堆是否许可，也要在目标构建约束中明确，而不是由extern "C"决定。

## 例子与推演

下面是头文件边界，内存布局由实现持有。这里只描述接口；读取失败如何报告、错误码含义及状态线程安全须和实现一起发布。

```c
#ifndef DEVICE_BOUNDARY_H
#define DEVICE_BOUNDARY_H
#include <stdint.h>
#ifdef __cplusplus
extern "C" {
#endif
struct device;
/* out非空；失败将*out置空；成功由device_destroy释放。 */
int device_create(uint32_t limit, struct device **out);
int device_read(struct device *owner, uint32_t *out);
void device_destroy(struct device *owner);
#ifdef __cplusplus
}
#endif
#endif
```

C++实现引用同一头文件，内部定义 struct device，并在create内部使用RAII组织失败路径。只有全部构造成功才把句柄转交给调用者。destroy是同一库提供的销毁入口，调用方不得自行delete/free。read输出失败不改还是清零必须选一个合同，不能要求调用方靠“上次值看起来合理”决定是否成功。

异步 C 回调再使用 C10 的函数指针+void*上下文；注销函数应说明何时不会再调用、是否等待已在飞行的回调。C++回调若可能抛出，也应在回调桥中转换，不能越过未经约定的C/RTOS调用栈。

## 常见误区与失败边界

- extern "C" 不使 C++重载组能按 C普通名字无限导出，接口要不同导出名
- 编译器、位数、结构packing、enum大小及调用约定不匹配，仍会破坏ABI
- 固定宽度字段不自动形成线协议，padding/字节序/版本与长度仍要编码
- 共享结构体中不能直接传进程本地指针供另一个进程解引用
- opaque handle不是运行时安全认证；无效句柄、二次销毁、并发访问仍需合同
- 封装一层C并不自动保证所有未来编译器的跨版本二进制兼容，应固定并测试目标组合

## 面试追问

为什么把拥有者对象藏进opaque handle？答：使调用方不依赖内部类布局，维持创建/销毁与资源责任的一致入口，允许实现改变。

为什么用户和库要各自编译头文件测试？答：同一接口必须同时被真正 C编译器和C++编译器接受，再由目标链接器证明链接符号匹配；只在 C++单文件中跑一遍不够。

## 动手练习与验收

仓库已有可运行的[双语言头文件](../../examples/cpp/device_boundary.h)、[C++实现](../../examples/cpp/device_boundary.cpp)与[真正C调用方测试](../../tests/host_c_abi_test.c)，由主机测试脚本分别编译再链接。实现用假计数资源，C++17 -fno-exceptions 与nothrow分配，不模拟真实设备。已测试空输出、非法初始限值、合法读取、耗尽后不改输出和空句柄销毁；分配失败注入、回调注销与无效非空句柄恢复未测。

扩展练习：分别用 gcc -std=c11 编译调用方，用 g++ -std=c++17 编译实现，再用 C++链接驱动程序链接两者。观察 nm符号，并逐项测试空输出、初始化失败、合法读、销毁空句柄、回调注销。不可恢复的无效句柄使用作合同坏例，不能宣称随意解引用后崩溃就是错误处理。

验收：头文件真正双语言可编译；每次成功create只有一条destroy责任；异常不越过明确的边界；记录目标ABI、编译选项、库版本及安全失败语义。主机实验不等于 MCU 启动或驱动验证。
