# C19 · 成员初始化顺序与 Rule Zero/Five 怎样维护对象不变量？

学习优先级：P0。语言基线：C++17；与 C08 的资源生命期、C09 的拷贝移动一起学习。

## 直接回答

成员初始化发生在构造函数体之前，顺序由类声明决定。先建立完整、有效的成员状态，再执行构造函数体；不要靠初始化列表的书写顺序改变依赖。资源类优先让 string、vector、unique_ptr 等成员承担资源管理，采用 Rule Zero。若必须自己管理资源，就明确拷贝、移动、赋值、析构的全部合同，通常按 Rule Five 逐项定义、default 或 delete。

## 原理拆解

非委托构造中，最派生类先初始化虚基类，再按基类列表顺序初始化直接基类，再按声明顺序初始化成员，最后执行构造函数体。析构清理已成功构造的部分时顺序相反。构造抛出异常，已经完成构造的基类/成员会析构，但完整对象的析构函数不会执行；把资源放进RAII成员才能覆盖这个失败窗口。

初始化与赋值不是同一操作。类类型成员如果先默认构造再在函数体赋值，可能有额外成本，也要求默认构造存在。内置整数的默认初始化却不进行一次“默认构造调用”，可能只留下不确定值，不能说它固定初始化两次。没有被显式初始化的标量应当在默认成员初始化或列表中得到明确初值。

默认拷贝按成员自己的语义工作：裸指针复制地址，string/vector复制内容，shared_ptr共享拥有，unique_ptr禁止拷贝。深拷贝不是任何有指针成员的类型都应强制采取的选择；先确定这个成员是拥有资源还是观察外部对象。自己声明析构、拷贝或移动操作会影响其余特殊成员的自动生成，不能想当然认为编译器仍补全全部操作。

## 例子与推演

```cpp
#include <array>
#include <cstddef>
#include <string>
#include <utility>
struct Frame {
    std::string label;
    std::size_t label_bytes;
    std::array<int, 3> samples{};
    explicit Frame(std::string text)
        : label(std::move(text)), label_bytes(label.size()) {}
    /* label_bytes是构造时记录，不承诺移动后源与当前label.size相同。 */
};
```

label 先声明，所以 label_bytes 可以从已经构造好的 label 读长度。samples 的默认成员初始化把三项置零；无需为此定义析构或拷贝操作。复制 Frame 时，string和array按其值语义复制，不会共享同一块可释放的裸字符缓冲区。label_bytes在这里明确为构造时记录；若业务要求它始终等于当前label.size()，更适合不缓存它、提供size()查询，或在每次更新及自定义移动中维护这个不变量。

若把 label_bytes 声明在 label 前，即使列表仍把 label 写在最前，也不能让它先构造。不要运行“先访问未构造成员”的坏版本去猜输出，应修正声明依赖，并开启 -Wreorder。

对不能复制的设备句柄，删除拷贝并提供满足资源转移合同的移动；源进入可析构但不再拥有设备的状态。若用 unique_ptr 做成员且没有自定义特殊成员，默认操作已能表达这类所有权。禁止拷贝是合法设计，不是必须额外写一个深拷贝。

## 常见误区与失败边界

- 默认构造函数不只“零参数”：所有非参数包参数有默认值也可满足默认构造条件
- const/引用成员不能在函数体里重新初始化，但 C++11 起默认成员初始化可以表达某些初值
- new char(20) 创建一个值为20的字符；new char[20] 才是20个字符，后者要匹配delete[]
- explicit 控制隐式转换参与情况，不等于任何调用必须手写类型强转
- 对成员使用 memcpy 不会替含资源的 C++ 类执行合法拷贝构造
- noexcept 移动承诺必须真实；抛出异常的 noexcept 路径会终止程序

## 面试追问

为什么自定义一个析构函数就要检查移动能力？答：用户声明析构函数会抑制隐式移动构造/移动赋值等自动生成条件，类型可能改为拷贝或无法完成操作。

浅拷贝是否一定错？答：观察指针或共享所有权可能需要共享目标；错误在于复制后释放责任与访问合同不一致。
