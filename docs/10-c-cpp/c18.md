# C18 · atoi、strtol 与有界数值解析怎样定义失败合同？

学习优先级：P0。语言基线：C11；网络/设备输入视为带长度的字节序列。

## 直接回答

先定义输入语法、目标范围、是否允许尾字符和失败输出，再选函数。atoi/atof 不能提供健全的错误报告；strtol/strtod 提供转换终点与范围信息，但仍要检查。对于不是零结尾的协议字段，显式长度的解析器更容易证明读取范围。无论选哪种方案，都应在溢出发生前检查，而不是计算完再截断。

## 原理拆解

strtol 可以跳过前导空白并接受一个可选符号，遇到不属于数字部分的字符停止。这种“转换前缀”的合同不等于“整个字段合法”。errno 应在调用前清零；转换后分别检查 end == input、ERANGE、剩余字符和业务范围。返回 0、LONG_MIN 或 LONG_MAX 本身不足以判断失败，因为这些值也可能是合法结果。

base=0 会引入不同进制前缀；固定十进制协议应明确选择 10。目标为 int32_t 时，即便 long 能表示更大范围，也要再检查 INT32_MIN..INT32_MAX。浮点解析还要规定是否接受 NaN、Inf、指数、区域设置小数点与有限范围；使用 strtod 后可结合 endptr、ERANGE、isfinite 与业务校验，不把一个不完整手写 atof 当作标准库替代。

无符号累计方便处理 INT32_MIN 的额外一个负幅度。设下一位 d 为 0..9，允许幅度上限为 limit，在 acc * 10 + d 前验证 acc <= (limit - d) / 10。负号最大幅度为 INT32_MAX+1；最终遇到该幅度直接生成 INT32_MIN，避免先对 INT32_MIN 取负。

## 例子与推演

仓库原创接口：[numeric_parse.h](../../examples/c/numeric_parse.h)、[实现](../../examples/c/numeric_parse.c)。

```c
bool parse_i32_span(const char *data, size_t n, int32_t *out);
```

合同：精确十进制字节范围，可选一个 + 或 -，至少一位数字；不接受空白、尾字节、范围内的零字符。data/out 为空或 n 为0均失败；失败不改变 *out。输入无需零结尾，-0 得到0。调用方仍须保证 data 指向至少 n 个可读字节，检查长度不使非法地址自动合法。

```c
const char field[3] = {'-', '4', '2'};
int32_t value = 99;
/* 成功：没有终止零，也只读这3字节。 */
bool ok = parse_i32_span(field, sizeof field, &value);
/* 失败：完整字段中有额外非数字，value保持-42。 */
bool rejected = !parse_i32_span("12x", 3, &value);
```

这不是 strtol 的复刻，而是更严格的协议合同。不能把此函数用于需要小数、指数或区域设置语法的字段。

## 常见误区与失败边界

- atoi("bad") 和 atoi("0") 均可能得到0；不能据此区分错误与合法零
- 标准 atoi 的越界不保证饱和；“超范围变INT_MAX”是自定义合同
- 检查有符号乘加的结果时，UB 可能已经发生
- 返回成功不代表数值在业务范围内，例如合法 int32_t 不一定是合法波特率
- 只检查 errno 会漏掉没数字和合法前缀后带垃圾；失败不改输出便于避免半更新配置

## 面试追问

为什么直接用 strlen 给接收缓冲区求长度不可靠？答：协议字段未承诺终止零，会越过有效范围；帧解析器应该提供已核验的跨度。

如果允许前导/尾空白怎么处理？答：明确协议语法，在边界内先处理空白或另建解析接口，不悄悄修改已发布合同。
