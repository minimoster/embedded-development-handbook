# C17 · 宏、inline 与 constexpr 怎样避免重复求值和控制流陷阱？

学习优先级：P0。语言基线：C11、C++17；标明 GNU 扩展与标准语法。

## 直接回答

宏替换记号，函数调用执行已定义的类型与参数合同。给宏参数加括号能修复优先级问题，却不能防止重复求值。能用带类型的小函数表达的操作，优先使用 C 的 static inline 或 C++ 函数/模板；常量优先使用适合语言版本的 enum、const 或 constexpr。inline 不保证消除函数调用，constexpr 不保证每次调用都在编译期执行。

## 原理拆解

宏看起来像函数，却没有独立的参数对象。一个参数出现在条件表达式和选中分支中，就可能求值两次。若参数是读清零寄存器、取队列元素或 i++，这会改变实际操作次数。预处理器不检查类型，但展开后的 C/C++ 表达式仍需满足类型规则。

多语句宏要表现为一条语句，常见形式是 do { ... } while (0)，由调用方写分号。这解决 if/else 绑定和多语句问题，不自动解决变量名碰撞、重复求值、别名或溢出。参数在宏中只有一次文本出现也不意味着任何宏都能任意传入副作用表达式，仍应检查求值上下文。

C 的头文件小函数常使用 static inline，避免把 C99/C11、GNU89 与 C++ 的外部 inline 链接规则混为一谈。C++ inline 还允许符合 ODR 条件的定义出现在多个翻译单元。是否展开调用由优化器和目标条件决定；inline virtual 在语言上完全合法。

## 例子与推演

```c
static inline unsigned smaller_u(unsigned a, unsigned b) {
    return a < b ? a : b;
}
static inline void swap_u(unsigned *a, unsigned *b) {
    unsigned saved = *a;
    *a = *b;
    *b = saved;
}
```

调用 smaller_u(next_sample(), limit) 时，next_sample() 作为实参只执行一次；不要把这个保证扩大成“所有实参总按从左到右计算”。swap_u 要求两个指针有效，它们指向同一个对象也保持原值。使用临时值不会造成异或交换的同址清零，也不会进行可能溢出的有符号加法。

C++17 可写 constexpr unsigned smaller(unsigned a, unsigned b)，并用 static_assert 验证常量输入。传入运行时寄存器读数时，调用可以仍在运行时执行。函数模板提供类型层面的复用；是否允许混合类型、返回引用及临时对象，需要另行规定，不能直接把宏换成任何模板就宣布安全。

## 常见误区与失败边界

- 完整括号不解决多次求值；do/while 包装不解决副作用参数
- sizeof(a)/sizeof(a[0]) 只在 a 为真实数组对象时给出元素数，指针及调整后的数组形参不符合前提
- const 是否能作整数常量表达式，要分 C/C++；最终是否占存储，还受使用方式与优化影响
- 宏定义不占独立对象存储，不代表展开出的代码或字面量没有空间成本
- 清理资源的 C goto 标签可比重复错误路径更清楚；不要把“没有goto”当作正确性验收

## 面试追问

为什么不用无临时变量交换？答：工程目标是保持类型、别名及溢出合同；临时值的源代码并不代表编译器一定在内存中增加一次存取。

为什么 MMIO 参数尤其不宜传给重复求值宏？答：一次读可能带硬件副作用，重复读不只是变慢，而是改变外设状态。

## 动手练习与验收

用一个计数式 next_sample 函数测试单次求值；再分别在 if/else、同址交换、极端数值、真实数组/指针形参中检查接口。用 gcc -E 或 g++ -E 看实际展开，打开 -Wall -Wextra -Wconversion。错误宏作静态推演，不用已知 UB 的运行结果证明规律。

验收：解释每个参数的求值次数，证明交换的别名与数值边界，区分常量表达式与优化结果；检查两个源文件共同包含头文件的链接行为。
