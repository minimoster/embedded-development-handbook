# LX13 · fork、exec、wait 与僵尸回收怎样形成完整生命周期？

学习优先级：P0。先独立回答，再展开机制与验证。

## 直接回答

fork 创建子进程；exec 成功后用新程序替换当前进程的程序映像，PID 不变；wait/waitpid 由父进程取得子进程状态并完成回收。子进程退出与父进程回收是两件事，退出但尚未回收的子进程可处于僵尸状态。不能靠给僵尸发送 kill 来让一个已结束的执行流再退出一次。

## 原理拆解

把生命周期拆成创建、运行、退出、回收四个阶段。fork 返回负值是失败，父进程得到子 PID，子进程得到 0。Linux 通常采用写时复制：父子地址空间逻辑独立，普通变量的写入不是 IPC；继承的 fd 却可指向同一个 open file description。

exec 的 argv 是以 NULL 结尾的指针数组，环境与 PATH 搜索由所选接口决定；成功不返回，失败仍在旧程序中运行，必须走明确错误退出。父进程用 waitpid 处理指定孩子或循环处理所有已退出孩子：返回正数表示回收一个，WNOHANG 时 0 表示尚无可报告变化，-1 检查 EINTR/ECHILD 等。读取 WEXITSTATUS 前必须先判断 WIFEXITED。

SIGCHLD 是通知，不是“通知一次必对应一个孩子”的计数器。普通控制流应把已结束孩子回收干净。父进程先退出时孩子可被 PID namespace 的 init 或最近 subreaper 接管，不能只背宿主 PID1。

## 例子与推演

网关启动一个日志辅助进程：父进程保存 child_pid，孩子成功 exec 日志程序，失败则用 _exit 返回约定失败码。父进程保留可恢复错误信息，等待时区分正常退出、信号终止和暂时仍运行。程序关闭时先停止产生新工作，再按已定义策略请求孩子退出，最后回收。

若两个孩子几乎同时退出，第一次 wait 只取走一个状态，第二个状态仍可等待。退出状态不会因为“同时退出”自动被第一次 wait 忽略。

## 常见误区与失败边界

多线程程序 fork 后，孩子只保留调用 fork 的线程，却继承了其他线程可能持有的锁状态；到 exec 前只调用允许的 async-signal-safe 接口。不要在此阶段随意 malloc、printf 或拿应用锁。posix_spawn 常能减少这类自管细节，但仍需检查其契约。

exit 会执行库层清理并刷新继承的 stdio 缓冲，_exit 不执行相同清理，二者不能随意互换。fork 并非复制所有物理页；mmap 也只有符合共享语义的映射才成为父子共享通信。不要为“清僵尸”直接杀生产服务父进程。

## 面试追问

问：为什么 exec 后还能等到同一个 PID？答：它替换程序，不新建进程。
问：wait(NULL) 会不会不回收？答：仍回收所等待孩子，只是不保存状态。
问：线程的 join 能否代替进程 wait？答：管理对象和资源不同，不能。

## 动手练习与验收

阅读并运行仓库原创 [Linux 生命周期实验](../../tests/host_linux_lifecycle_test.c)：仅创建实验自身的孩子，验证 _exit(7) 的状态、受控 exec 成功、再次 wait 得到 ECHILD。实验依赖 Linux /proc/self/exe，不是通用裸机程序。

扩展练习：创建两个实验孩子并故意推迟父进程回收，观察各自状态，再循环 waitpid 至没有可回收孩子。验收记录创建数、回收数、错误码和停止策略；不操作其他用户进程。主机实验不能证明目标 BSP 的进程监督已验证。
