# LX08 · 从应用性能问题到 CPU/内存/I/O 证据链？

学习优先级：P1。先独立回答，再展开机制与验证。

## 直接回答

先定义延迟/吞吐/丢包等指标，再分离 CPU 执行、等待 I/O、锁等待和调度。top 的单个百分比无法回答根因；记录负载、时间窗口、进程/线程与复现输入。

## 原理拆解

用户态/内核态、上下文切换、页缺失和缓存行为会改变性能。日志本身可能引入锁和 I/O。观测工具需与目标内核权限及符号匹配；主机基准不能直接当设备指标。

## 例子与推演

遥测延迟突然升高，记录入队、出队、开始编码、写出、响应五个时间点，找到队列堆积区间。再查对应线程是否 CPU busy、阻塞或锁争用，避免先猜网络差。

工具选项要和量度对应：procps vmstat 的 -a 显示 active/inactive 内存，-s 输出统计表，均不是列出所有活动进程。df看文件系统可用量，du看文件树占用，打开后已unlink的文件可能仍占空间；这时结合fd持有者证据，不能只看目录。

## 常见误区与失败边界

“CPU 不高所以程序不慢”忽略阻塞。“缓存越大越好”忽略堆积延迟与内存上限。不要公开真实用户数据、设备标识或密钥日志。

## 面试追问

如何避免日志改变结果？答：分级、采样、有界缓冲和独立复验；记录观测开销。

## 动手练习与验收

做受控 CPU 忙、睡眠、队列堵塞三个场景。验收：给时间线证据，结论限定测试环境并给下一项可证伪实验。
