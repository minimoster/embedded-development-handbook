# LX18 · select、poll、epoll 的资源上限与公平预算怎么验证？

学习优先级：P0。先独立回答，再展开机制与验证。

## 直接回答

epoll 没有 select 的同类固定 fd_set 位图约束，但仍受 fd、watch 数、内存和应用连接预算限制。select/poll/epoll 返回就绪线索，不返回完整业务消息。ET 常用非阻塞且处理到 EAGAIN；若因公平预算提前停，必须保留本地待处理状态，不能只重新睡等下一次边沿。

## 原理拆解

select 每次设置输入集合，并处理返回后被修改的集合；常见 glibc fd_set 限制是 FD_SETSIZE，讨论的是可安全放入集合的 fd 数值范围，不只当前监听个数。poll 用数组报告 revents，但仍要处理数组和应用分发工作。

epoll_ctl 管理内核 interest 集合，epoll_wait 从 ready 集合取事件并写入调用者提供的结果缓冲。“只传一次事件表地址”混淆了内核注册状态与每次结果输出。资源还包括 RLIMIT_NOFILE、max_user_watches、socket 缓冲、每连接状态和待发队列。

公平与 ET 完整消费必须一起设计：一次处理一定字节/时间预算，未到 EAGAIN 的连接放到本地 ready 队列继续处理；本地还有工作时不要无限睡在 epoll_wait。EPOLLOUT 关注应和待发数据/阻塞状态协调，避免持续就绪导致忙循环。

## 例子与推演

连接 A 持续有大量输入，B 每秒只发少量控制数据。如果对 A 无上限读到 EAGAIN，而生产速度始终跟上，B 可一直等不到服务。反过来，A 每次只读 1 KiB 就回到阻塞 epoll_wait，也可能留数据却再无边沿。

正确方案给 A 公平预算并标为本地仍就绪，轮转处理 A/B。连接容量再加内存预算：例如 N×每连接缓冲上限只是应用部分，还要加 fd、内核 socket 状态与队列。

## 常见误区与失败边界

“ET 总比 LT 快”“epoll O(1) 因为红黑树”“无资源限制”都不是完整结论。吞吐和时延取决于就绪比例、事件数量、用户处理和系统配置。LT 更易实现仍不代表消息完整或并发安全。

EOF、HUP、ERR 和缓冲中的剩余数据不能只当一个“断开”布尔。关闭/复用 fd 后必须防止旧事件和旧指针引用新连接；重复 fd 指向同一打开文件描述时，事件撤销语义还需核对。

## 面试追问

问：ET 读到预算上限即可结束吗？答：可以切换服务别的连接，但必须确保本地继续处理直到 EAGAIN，不能期待自动新边沿。
问：监听 100 个 fd 却有 fd=2000 为什么 select 也有问题？答：fd_set 约束涉及数值索引。
问：怎么选 LT/ET？答：先保证状态机、背压和测量可用，再按负载比较。

## 动手练习与验收

在自建 socketpair/pipe 测试中做三个 case：残留数据、热连接与冷连接、关闭后资源回收。记录 epoll_wait 次数、每连接最大等待、缓冲峰值。只读查询自身资源限制与系统 watch 设置，不改系统限制。

验收：ET 无残留停滞，冷连接不会被热连接无限压制，关闭后队列/fd/对象全部收敛。先读[LX03的就绪模型](lx03.md)，本页专门验证资源与公平边界。
