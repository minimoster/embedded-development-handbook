# LX15 · 教材调度算法、Linux 公平策略和实时上限怎样分层回答？

学习优先级：P1。先独立回答，再展开机制与验证。

## 直接回答

FCFS、SJF、RR 和多级反馈队列是分析模型；Linux 实际行为应按调度类、策略、内核版本和任务可运行状态解释。普通公平调度追求 CPU 分配公平与响应性；SCHED_FIFO/RR 用实时优先级规则；SCHED_DEADLINE 使用运行预算、期限和周期等参数。选“实时”策略本身不等于端到端期限已经满足。

## 原理拆解

先问任务能否运行，再问哪些任务竞争哪个 CPU，最后问同类任务如何选。阻塞等 I/O 的任务不在可运行竞争中；CPU 亲和性、cgroup、锁和中断工作都会影响实际等待。

FCFS 可让短任务等长任务；SJF 需要估算执行时间；RR 的时间片影响切换成本和响应。多级反馈的换队次数示例不等于实际上下文切换总数：新任务抢占、I/O 和同队竞争均会增加切换。

当前 Linux 公平调度文档使用 EEVDF 解释 eligibility/lag 与 virtual deadline；旧内核常用 CFS 的 vruntime 模型，目标版本须核对。FIFO 同优先级任务没有普通 RR 时间片轮转；RR 在同优先级间轮转，但高优先级持续可运行仍可压制低优先级。DEADLINE 的准入和预算控制也无法替代硬件/I/O/锁的整体可调度性分析。

## 例子与推演

三任务 A/B/C 到达时间为 0/1/2 ms，CPU 需求为 8/2/1 ms。FCFS 的完成顺序 A/B/C，响应等待分别 0/7/8 ms；抢占 SRTF 若在t=2 ms的同剩余时间平局中优先C，可先完成C/B，再完成A；平局保留当前B则先B/C，再A。这个小例子演示模型差异，没有复现 Linux 完整实现。

设备控制任务的期限 5 ms，平均运行 1 ms。若它偶尔等低优先级线程持有的锁 10 ms，提升线程优先级不能直接消除违约；先量出锁持有时间、IRQ 延迟和缺页影响，再选机制。

## 常见误区与失败边界

“只有一个 CPU”不能作为通用前提。“不会饥饿”需要有限任务/合理负载等假设。“实时优先级越高越好”可能让管理和恢复线程拿不到 CPU。教学公式 HRRN 应写为 (等待时间+服务时间)/服务时间。

不要把公平调度的虚拟期限当业务绝对 deadline；也不要把 FreeRTOS 的优先级数值方向、时间片规则照搬到 Linux。改生产调度策略需要风险评估，本卡的练习不用 root 调度权限。

## 面试追问

问：nice 和实时优先级是同一个数吗？答：不同策略中的不同参数。
问：为什么平均延迟达标仍会丢期限？答：目标是最坏边界或约定分位数，平均掩盖长尾。
问：调度策略如何验收？答：定义任务预算/期限、负载与统计，检查实际等待和执行，而不只看设置成功。

## 动手练习与验收

先在纸上模拟上述三任务的 FCFS、RR(2 ms)、SRTF，分别列首次运行、结束、等待与切换事件。再只读检查自建用户态测试线程的策略、CPU 亲和性和耗时，记录 uname 与内核版本。

验收：能明确“教材模型预测”与“Linux 实测”的不同；列出至少锁、中断、缺页和 I/O 四个未由策略自动解决的延迟来源。未取得环境和授权时，不修改系统实时策略，不宣称已验证硬实时。
