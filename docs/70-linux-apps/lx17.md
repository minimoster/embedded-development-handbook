# LX17 · 有界线程池怎样设计背压、拥有权和停止协议？

学习优先级：P1。先独立回答，再展开机制与验证。

## 直接回答

线程池复用工作线程，只解决反复创建线程的一部分成本。完整设计至少包括有界任务队列、队满策略、任务数据拥有权、异常/取消处理和停止协议。生产快于消费时，增加线程或无界堆积不能自动获得可伸缩性；要定义阻塞、拒绝、降采样或其他背压行为。

## 原理拆解

用状态而不是“被通知次数”驱动 worker：持锁检查队列非空或停止条件，条件不满足在条件变量上等待；唤醒后循环检查谓词。取走任务后释放队列锁，再执行耗时任务；完成时只更新必要统计。条件变量可虚假唤醒，通知不等于条件必然成立。

任务提交接口必须说明数据是复制、移动、共享拥有还是借用。若提交回调借用调用者栈变量，提交函数返回后 worker 可能访问悬空对象。队列容量应按内存、允许排队时延与突发预算决定，而不只按“装得下”。

关闭可选 drain（执行已接受任务）或 cancel-pending（取消尚未执行），但要明文约定。先关闭接收入口，更新停止状态并唤醒所有 worker，等待运行中任务结束/join，最后释放队列和上下文。重复 stop、部分 worker 创建失败都要有一致退路。

## 例子与推演

4 个 worker，每个任务平均 25 ms，理想平均处理能力约 160 个/秒。输入 200 个/秒会以约 40 个/秒积压；空的 100 个任务队列在这种理想模型下约 2.5 秒填满。同步开销、长尾任务与 I/O 会让真实容量不同，数字必须实测。

遥测任务可以合并旧数据并统计丢弃；命令控制任务可能需要立即拒绝并返回可重试错误。它们不能用同一“悄悄丢弃”策略。

## 常见误区与失败边界

“一个请求一个线程”不是所有多线程服务器唯一模型。“线程池一定比多进程快”忽略隔离、锁竞争、CPU/I/O负载。线程数超过可用资源可能放大切换和内存占用。

不要在队列锁内调用用户任务，也不要只设置未同步 bool 就销毁上下文。worker 提交任务再同步等同一小线程池处理，可能造成池内等待死锁；先画依赖图。取消运行中任务不是简单 free 掉参数。

## 面试追问

问：队满了为什么不总增加线程？答：任务可能受单核、锁、设备或外部服务限制，扩容不一定增容量。
问：notify_one 会不会丢任务？答：任务存在于队列，谓词循环保证可发现；不是靠通知数存任务。
问：怎样证明优雅关闭？答：所有已接受任务最终完成或明确取消，所有 worker 可等待退出，引用归零。

## 动手练习与验收

实现只处理本地纯计算任务的小池，给出队列容量、拒绝返回值和 drain 策略。注入队满、任务失败、第 N 个线程创建失败和重复停止，使用适用 sanitizer 检查竞争/生命周期。

验收：停止后 attempted=accepted+rejected，accepted=completed+cancelled（attempted为所有提交尝试，accepted为已接收任务，运行中任务已退出后再核对），队列峰值不超过容量，停止后不再接收，所有 joinable worker 最终 join。统计模型和测试计划为原创设计，不把未运行的压力测试写成通过。
