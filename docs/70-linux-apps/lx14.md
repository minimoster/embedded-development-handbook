# LX14 · fd、打开文件描述、inode 与 unlink 的生命周期怎么区分？

学习优先级：P0。先独立回答，再展开机制与验证。

## 直接回答

fd 是进程 fd 表里的整数索引；open file description 保存一次打开的偏移和状态等信息；inode 表示文件系统对象，目录中的名字把路径和对象关联。dup 或 fork 可让不同 fd 指向同一个打开文件描述，分别 open 同一路径通常产生不同打开文件描述。unlink 删除名字，不等于立刻销毁仍被打开的对象。

## 原理拆解

路径查找由目录和 VFS 名称缓存等参与；找到对象后，open 建立打开文件描述并返回 fd。fd 的 FD_CLOEXEC 与 open file description 的 O_NONBLOCK 等文件状态标志属于不同层。

dup 创建新的 fd，但共享原来的文件偏移与文件状态；fork 复制 fd 表项，也可继续指向相同打开文件描述。两个相同整数 fd 若位于不同进程，不证明它们指向同一对象。关闭一个 fd 只是释放这个引用，其他引用可继续使用。

硬链接是同一文件系统对象的新名字，不复制 inode。符号链接是路径引用，目标可以不存在。最后一个名字被 unlink 后，仍打开的普通文件仍可读写；相应引用最终释放才满足回收条件。目录项、VFS dentry、inode 和磁盘数据块不是同一个东西。

## 例子与推演

实验打开临时文件并写入 ABCD，定位到开头后 dup。原 fd 读 A，复制 fd 再读就得到 B，因为共享偏移。另一次 open 同一路径的 fd 仍有自己偏移，可从 A 读起。

随后 unlink 名字，按路径再 open 会失败，但原 fd 可继续读。真实日志轮转若只删除仍被写的文件，磁盘占用可能还在；证据应查看持有者和打开引用，而不只看目录里有没有名字。

## 常见误区与失败边界

“删除文件就是删除 inode”漏掉名字计数和打开引用。“每个 fd 一定对应不同 file”错在 dup/fork。“inode 号全系统唯一”也不严谨，它的身份必须结合文件系统。符号链接的路径可能是相对链接所在目录的路径，不是进程当前工作目录。

关闭期间另一个线程可能复用相同 fd 数字；应先撤销异步访问、明确对象所有权，不能把旧整数永久当唯一连接 ID。不要依据链接类别笼统断言性能和空间总量。

## 面试追问

问：dup 后修改 O_NONBLOCK 影响谁？答：共享同一打开文件描述的相关 fd；FD_CLOEXEC 则是各 fd 的标志。
问：unlink 后为何 df 没马上下降？答：可能还有打开引用；也需考虑文件系统其他占用证据。
问：如何避免辅助 exec 继承秘密 fd？答：从创建起使用适用 CLOEXEC 机制，避免并发设置窗口。
