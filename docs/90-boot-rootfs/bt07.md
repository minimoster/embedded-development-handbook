# BT07 · 交叉编译 Linux 内核后怎样验证目标部署契约？

学习优先级：P1。先独立回答，再展开机制与验证。

## 直接回答

内核编译成功只证明一组构建输入生成了产物；部署成功还需架构、配置、镜像格式、DTB、modules、rootfs 与 bootloader 对齐。交叉构建时应隔离输出和安装目的地，不能把在开发机执行 make install/modules_install 当作“安装到板子”。

## 原理拆解

记录源码 commit/版本、ARCH、工具链前缀、配置与输出目录。先选择目标支持的 defconfig 或已有配置，再按需求修改并保存；菜单配置与 savedefconfig 各有职责。CROSS_COMPILE 通常是工具前缀而非完整 gcc 命令，结尾连字符等细节需依据实际工具链核对。

构建目标依架构和板级流程选择，如 Image/zImage、dtbs、modules；不是所有内核输出固定 .bin。分清开发机输出、staging rootfs 和目标存储。INSTALL_MOD_PATH 指向 staging 目的地，模块通常按 kernel release 存放；还需匹配目标内核配置、符号版本与实际 ABI。编外模块应使用对应目标构建树和 Kbuild，不用主机 /lib/modules 路径猜测。

启动阶段核对加载的真正文件、地址和启动项；内核起来后检查 uname、cmdline、所用 DT 与模块加载日志。产物版本匹配但硬件/驱动错误仍可能无法启动，保留可回退入口和旧镜像。

## 例子与推演

开发机 x86_64，为 AArch64 板构建：输出进独立目录；目标模块安装到自建 staging，而不是宿主 /lib/modules。把 Image、匹配 DTB 和 staging 中所需模块装入目标镜像后，确认启动日志显示预期 kernel release。

若应用报设备不存在，可能是模块未部署、加载失败、DT 未匹配或节点创建链缺失。不要只重跑编译，先定位构建→打包→加载→probe→用户接口哪一步断了。

## 常见误区与失败边界

make deconfig 不是通用配置目标，实际配置入口要查目标树；CROSS_COMPILE 与 PATH 命令应分开核对。未设置安装目的地的命令可能修改宿主系统。

外部模块的 modules_prepare 不一定产生完整符号版本信息；开启相应配置时可能需要完整内核构建。insmod 成功/失败、module_init、probe 是不同阶段；init 成功不保证所有设备已绑定。模块移除前停止异步工作并处理正在使用的对象，不能只列申请/释放两列就完事。

## 面试追问

问：应用能运行为何模块仍不兼容？答：用户态 ABI 与内核模块 ABI 是不同约束。
问：为什么有 Image 还要 DTB 和模块？答：内核执行代码、硬件描述与可选驱动各有职责。
问：安装该发生在哪？答：按项目 staging/镜像流程设置明确目标，不能依赖宿主默认路径。

## 动手练习与验收

先写一份构建/部署清单，列所有输入、产物、校验值、staging 位置、目标启动项与回退步骤。主机上只做工具链存在性和命令规划检查，不运行宿主安装。

有专用目标/QEMU 环境后再执行构建与受控部署并保存日志。验收必须分别勾选：编译、打包、启动、模块匹配、设备 probe、应用接口。未获得内核树/BSP/目标日志时，不写“已验证板级移植”。
