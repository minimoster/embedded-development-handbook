# BT08 · U-Boot 的 bootm、booti 与内核入口契约怎样核对？

学习优先级：P0。先独立回答，再展开机制与验证。

## 直接回答

启动内核应先核对镜像格式、命令语法、内存布局和目标架构入口契约。bootm 常用于 FIT/legacy 等镜像，booti 用于支持的 Linux Image 格式；它们的内核、ramdisk、DT 参数主要是位置参数/配置选择，不能把 bootm -d/-s 当作通用内核启动语法。bootargs 与 /chosen 信息、寄存器传递属于不同层。

## 原理拆解

分清磁盘文件、加载地址、解压/搬移地址和执行入口。内核存成 rootfs 里的一个文件只改变加载来源，不把它变成用户态程序。extlinux.conf 是启动配置的一种来源，不意味着必须“把内核当应用装进 ramdisk”才能启动。

U-Boot 文档中的 booti 形式为 kernel 地址、可选 initrd[:size] 和 DT 地址；无 initrd 而有 DT 时用占位 '-'，raw initrd 需要明确大小。bootm 的 FIT 可用 #configuration 或 :subimage 选择，legacy 支持取决于构建配置。真实设备以 help 输出、版本和启用命令为准。

常见 AArch64 直接入口契约要求 x0 为 DTB 物理地址，保留寄存器按规定置值，满足异常级/中断/MMU/cache 等条件。入口要求不等于 U-Boot 全程必须关 cache；cache 与地址翻译不同，交接还需清除陈旧指令/维护可见性。看门狗是否能关闭取决于芯片和安全/运维要求，应设计喂狗或移交，而不是一律关闭。

## 例子与推演

已确认目标支持 booti 且 Image/DTB 已加载到互不重叠的合法区域，无 initrd 时可规划 booti ${kernel_addr_r} - ${fdt_addr_r}。此例只展示参数位置；变量的具体数值必须来自板级内存图，不能复制另一块板的地址。

若加载 initrd 后再加载其他文件，filesize 可能被后一次加载覆盖，不能把它直接当旧 initrd 大小；应明确保存每个镜像的大小并检查区间不重叠。启动后用 /proc/cmdline 和日志核对实际参数。

## 常见误区与失败边界

“所有 Linux 都先 BIOS/GRUB，再内核自己解压”不适用于所有嵌入式链；AArch64 Image.gz 通常要求 loader 做适当解压。ARM32 SVC 模式描述不能直接移植为 AArch64 入口说明。

“关数据 cache 防指令取址”“开 cache 访问的是缓存地址而不是物理地址”混淆机制。启动失败也可能来自 console/DTB、内存保留区、错格式或未停止 DMA。不要为消除不确定性随意清除环境或写 Flash；先只读核查并准备回退。

## 面试追问

问：rootfs 中放内核为何还能启动？答：bootloader 读取文件并加载执行，不是用户态 exec。
问：DTB 是传大小还是地址？答：依架构入口/API，AArch64 直接入口主要通过 x0 地址及 DTB 自身结构描述；不是一概发明命令选项。
问：关 MMU 为什么不等于关 cache？答：翻译与缓存是不同职责，入口规范分别约束。

## 动手练习与验收

写一份仅供目标板核查的交接表：ROM/SPL/U-Boot 版本、Image/FIT 类型、已启用命令、RAM/保留区、各镜像加载/解压区间、DTB、cmdline、串口与回退入口。先在日志/命令帮助中逐项确认。

验收：每个地址有板级来源，命令与格式匹配，initrd 大小未被覆盖，入口要求有官方架构依据。未获得专用目标/QEMU 与授权时不实际启动/写 Flash，不写“已完成移植”。
