# IC02 · 停止采集后删队列，下一次中断 HardFault

原创场景，公开面经只提供主题联系，非原帖题目或公司题库。核对日：2026-10-10。主机状态模型、板级DMA、Flash断电和内核模块练习均未执行；下列验收是后续检查标准。

## 公开面经主题联系

[EN05](source-catalog.md#en05)/[EN08](source-catalog.md#en08) 的中断、任务与RTOS项目追问；关闭流程为原创延伸。

## 故障场景

控制任务收到 stop，立刻 vQueueDelete，再 vTaskDelete 消费者。采集定时器、DMA和串口中断仍可能在运行，偶尔访问旧队列句柄。

## 先理解机制

释放资源像拆桥，必须先阻止车继续上桥，再确认桥上已经没人。把变量改成 NULL 只会影响之后重新读取这个变量的代码，不能取消已保存的旧指针。

## 直接回答

我把关闭变成协议：RUNNING→STOPPING→QUIESCENT→RELEASED。先拒绝新请求，停止硬件生产和回调入口，再确认在途 DMA/ISR 不再访问对象。消费者清理自己拥有的应用缓冲、发送停止确认，此后不再访问共享对象；本练习采用“确认后停泊，由控制任务删除一次”的终止方式，最后删除队列。若改成消费者自删，控制任务不能再次删除旧任务句柄，任务函数也不能直接return。vTaskDelete 不自动释放任务自己申请的应用内存。[官方 task.h](https://raw.githubusercontent.com/FreeRTOS/FreeRTOS-Kernel/V11.1.0/include/task.h) 动态创建队列的删除会释放内核分配的队列存储；xQueueCreateStatic使用的存储仍由应用管理，删除不会替应用free。删除队列也不会替应用释放队列项指向的缓冲。两者都不是设备停止操作。[官方 queue.h](https://raw.githubusercontent.com/FreeRTOS/FreeRTOS-Kernel/V11.1.0/include/queue.h)；动态/静态分配的删除分支见[固定版本 queue.c](https://raw.githubusercontent.com/FreeRTOS/FreeRTOS-Kernel/V11.1.0/queue.c)

## 面试追问

1. “关 NVIC 就可以释放？”还需处理外设中断源、DMA活动、待决状态和已进入的处理路径；每项顺序由芯片参考手册及 HAL 合约决定。不能把一个关中断 API 当作全部硬件静止证明。
2. “消费者永久阻塞在队列怎么办？”在队列仍有效时安排 stop 消息/超时检查等退出协议。控制路径不应等待一个永远无法收到退出条件的任务；不要让 stop 消息因队列满而静默丢弃。
3. “重启时复用原句柄地址？”旧回调还持有地址时可能误写新对象。可附会话代号帮助检测迟到事件，但代号不能替代停止生产者与寿命同步。

## 常见误区与失败边界

在 ISR 删除对象；先free缓冲再终止DMA；拿消费者需要的锁等待其退出；把任务被删理解为其所有外设/软件定时器自动停止。

## 动手练习（尚未执行）

写一个主机状态模型，用事件列表枚举“stop前/后到达ISR”“队列满”“消费者正处理”“重复stop”“重新start”。每个资源记录 live、owner、session。禁止任何事件访问 RELEASED 资源。板级验证另需逻辑分析仪/寄存器日志，主机模型不能证明外设已停。

## 验收标准（尚未执行）

- 删除发生前所有生产者已静止、消费者退出得到确认
- 重复stop不重复释放；重启后旧session事件被拒绝
- 关闭有超时失败路径，超时不能强行释放仍在使用的资源

## 版本与适用边界

FreeRTOS V11.1.0对象寿命；关闭状态机是原创设计，不是FreeRTOS自带join或设备shutdown保证。Cortex-M具体停DMA/清中断顺序未执行、未给通用寄存器答案。
